# 蒸馏塔 - 可分组扩展的机器

本文演示一台**可分组扩展**的蒸馏塔。蒸馏塔的"段数"可以根据配方的需求动态拼装，1 段、2 段、3 段都是同一台机器。

本文按 26.1.2 提交 `f234477b` 核对。机器在 startup 固定注册，结构在 server 重载事务中提交，配方由 `ServerEvents.recipes` 注册。后两者支持 `/reload`；机器的外观、配方池与可扩展开关修改后需重启。

代码对应三个文件：

- `example/startup_scripts/A_Group_Machine.js`
- `example/server_scripts/structure/A_Group_Machine.js`
- `example/server_scripts/recipe/A_Group_Machine.js`

## 概览

蒸馏塔 与 [高炉](高炉) 的关键差异在于**结构形态**：

- 高炉 用扁平式 `.pattern(...).set(...).controller(...).build()`，是一个**单一**结构。
- 蒸馏塔 用阶段式 `.mainStructure(...).expandStructure(...).expandStructure(...)`，是**一组**结构的合集。

玩家可以选择搭 1 段、2 段或 3 段，对应结构阶段 1、2、3。这是 stage，不是 [热能冶炼炉](热能冶炼炉) 的 level 类型与线圈等级。

蒸馏塔是分组结构的经典场景：蒸馏每一级都需要独立的端口与外壳。如果只有 1 级，玩家就是"小型蒸馏塔"，3 级就是"大型蒸馏塔"。

MMCR 用**端口族并集 + 结构阶段枚举**让一台机器 ID 同时覆盖多种形态。

`expandableStructure(true)` 是本机器在启动期的关键开关，它告诉 MMCR "这台机器的结构是一组阶段而不是单个结构"。

详见 [MachineBuilderJS.expandableStructure](../API/KubeJS#machinebuilderjs)。

## 机器定义

`startup_scripts` 目录下的 [A_Group_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/startup_scripts/A_Group_Machine.js)：

```js
// Register a machine with an expandable structure.

MMCREvents.startup(event => {

    const distillation_tower = event
        .createMachine("mmcr_kubejs:kubejs_distillation_tower")
        .displayNameKey("machine.mmcr_kubejs.kubejs_distillation_tower")
        .recipePool("mmcr_kubejs:kubejs_distillation_tower")
        .appearance("minecraft:polished_blackstone")
        .expandableStructure(true) // Enable the expandable structure.

    distillation_tower.register()

    // See server_scripts/structure/A_Group_Machine.js for the grouped structure.
})
```

`event.createMachine(...)` 返回 [MachineBuilderJS](../API/KubeJS#machinebuilderjs)。链式调用：

- `.createMachine()`：注册 ID `mmcr_kubejs:kubejs_distillation_tower`。
- `.displayNameKey(...)`：本地化键。
- `.recipePool(...)`：配方池 ID。详见 [MachineBuilderJS.recipePool](../API/KubeJS#recipepool-string-recipepoolids-%E2%86%92-machinebuilderjs)。
- `.appearance()`：把控制器外观设为磨制黑石。详见 [MachineBuilderJS.appearance](../API/KubeJS#machinebuilderjs)。
- **`.expandableStructure(true)`**：声明这台机器的结构是分组结构，可扩展。详见 [MachineBuilderJS.expandableStructure](../API/KubeJS#machinebuilderjs)。
    本例用 `.mainStructure(...)` + `.expandStructure(...)` 声明三个完整形态；这不是开关强制的唯一声明方式。

启动期窗口不可热加载，修改后必须重启游戏。

## 多方块结构

`server_scripts/structure` 目录下的 [A_Group_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/server_scripts/structure/A_Group_Machine.js)：

```js
MMCREvents.server(event => {
    const api = event.getAPI()
    const structure = event.createStructure("mmcr_kubejs:kubejs_distillation_tower")

    // Define the main structure of the distillation tower.
    structure
        // Use mainStructure to define the main section.
        .mainStructure(stage =>
            stage
                .pattern(['  XXX  ','  AAA  ','       ','       '])
                .pattern([' XXXXX ',' B   B ','  ACA  ','       '])
                .pattern(['XXXXXXX','A     A',' B   B ','  DDD  '])
                .pattern(['XXXXXXX','A     A',' B   B ','  DDD  '])
                .pattern(['XXXXXXX','A     A',' B   B ','  DDD  '])
                .pattern([' XXXXX ',' B   B ','  BBB  ','       '])
                .pattern(['  XXX  ','  BEB  ','       ','       '])
                .set('C', api.anyOf(
                    api.anyOfItemInput(),
                    api.anyOfItemOutput(),
                    api.anyOfEnergyInput(),
                    api.block('minecraft:deepslate_bricks')
                ))
                .set('X', api.block('minecraft:polished_blackstone'))
                .set('A', api.block('minecraft:deepslate_bricks'))
                .set('B', api.block('minecraft:polished_blackstone_bricks'))
                .set('D', api.block('minecraft:gilded_blackstone'))
                .controller('E')
        )
        // Use expandStructure to define an additional section.
        .expandStructure(stage => stage
            .pattern(['  XXX  ','  AAA  ','       ','       ','       '])
            .pattern([' XXXXX ',' B   B ','  ACA  ','  ACA  ','       '])
            .pattern(['XXXXXXX','A     A',' B   B ',' B   B ','  DDD  '])
            .pattern(['XXXXXXX','A     A',' B   B ',' B   B ','  DDD  '])
            .pattern(['XXXXXXX','A     A',' B   B ',' B   B ','  DDD  '])
            .pattern([' XXXXX ',' B   B ','  BBB  ','  BBB  ','       '])
            .pattern(['  XXX  ','  BEB  ','       ','       ','       '])
            .set('C', api.anyOf(api.anyOfItemInput(), api.anyOfItemOutput(), api.anyOfEnergyInput(), api.block('minecraft:deepslate_bricks')))
            .set('X', api.block('minecraft:polished_blackstone'))
            .set('A', api.block('minecraft:deepslate_bricks'))
            .set('B', api.block('minecraft:polished_blackstone_bricks'))
            .set('D', api.block('minecraft:gilded_blackstone'))
            .controller('E')
        )

        .expandStructure(stage => stage
            .pattern(['  XXX  ','  AAA  ','       ','       ','       ','       '])
            .pattern([' XXXXX ',' B   B ','  ACA  ','  ACA  ','  ACA  ','       '])
            .pattern(['XXXXXXX','A     A',' B   B ',' B   B ',' B   B ','  DDD  '])
            .pattern(['XXXXXXX','A     A',' B   B ',' B   B ',' B   B ','  DDD  '])
            .pattern(['XXXXXXX','A     A',' B   B ',' B   B ',' B   B ','  DDD  '])
            .pattern([' XXXXX ',' B   B ','  BBB  ','  BBB  ','  BBB  ','       '])
            .pattern(['  XXX  ','  BEB  ','       ','       ','       ','       '])
            .set('C', api.anyOf(api.anyOfItemInput(), api.anyOfItemOutput(), api.anyOfEnergyInput(), api.block('minecraft:deepslate_bricks')))
            .set('X', api.block('minecraft:polished_blackstone'))
            .set('A', api.block('minecraft:deepslate_bricks'))
            .set('B', api.block('minecraft:polished_blackstone_bricks'))
            .set('D', api.block('minecraft:gilded_blackstone'))
            .controller('E')
        )

        // Build the grouped structure.
        structure.build()
})
```

`MMCREvents.server(event => {...})` 回调里的 `event` 是 [MMCRServerEventJS](../API/KubeJS#mmcrservereventjs)。

`event.getAPI()` 返回 [KubeJSApi](../API/KubeJS#kubejsapi)。

结构分三个阶段：

1. **`.mainStructure(stage => ...)`**：基础段。
详见 [MachineStructureBuilderJS.mainStructure](../API/KubeJS#machinestructurebuilderjs)。
每个阶段回调收到的 `stage` 是 [MachineStructureStageBuilderJS](../API/KubeJS#machinestructurestagebuilderjs)。
2. **第一个 `.expandStructure(stage => ...)`**：两段塔的完整形态。
详见 [MachineStructureBuilderJS.expandStructure](../API/KubeJS#machinestructurebuilderjs)。
3. **第二个 `.expandStructure(stage => ...)`**：三段塔的完整形态。

:::warning 注意
`structure.build()` 是在结构链式调用的**外层**调用。

`structure.mainStructure(...).expandStructure(...).expandStructure(...)` 三段配置完后，回到 `structure` 上再 `.build()` 终结。

运行时由完整模式匹配决定阶段，按高阶段到低阶段尝试，不是仅统计方块数量。
:::

每段内的字符定义完全相同：

- `'X'` → 磨制黑石
- `'A'` → 深板岩砖
- `'B'` → 磨制黑石砖
- `'D'` → 镶金黑石
- `'E'` → 控制器
- `'C'` → `api.anyOf(...)` 联合谓词：物品输入端口 ∪ 物品输出端口 ∪ 能量输入端口 ∪ 深板岩砖。也就是说每一段中部允许玩家摆端口或装饰方块。

阶段式 API 与扁平式 API 不能混用。一旦调用 `.mainStructure(...)`，再调用扁平的 `.pattern(...)` / `.set(...)` 会抛 `IllegalStateException`。

详见 [MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs) 的注意事项。

`.build()` 终结构建并提交。

## 配方

`server_scripts/recipe` 目录下的 [A_Group_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/server_scripts/recipe/A_Group_Machine.js)：

```js
ServerEvents.recipes( event => {
    event.custom({
        type: 'mmcr:machine_recipe',
        recipe_pool: 'mmcr_kubejs:kubejs_distillation_tower',
        tick_time: 300,
        allow_partial_outputs: true, // 允许部分接收输出，未接收的部分丢弃。
        requirements: [
            { type: 'minecraft:item', io: 'input', item: '#minecraft:logs', count: 1 },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: { id: 'minecraft:coal', count: 3 }
            },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: { id: 'minecraft:charcoal', count: 4 }
            },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: { id: 'minecraft:gunpowder', count: 3 },
                chance: 0.2
            },
            { type: 'neoforge:energy', io: 'input', fe_per_tick: 20 },
            { type: 'mmcr:stage', min_stage: 2 }
        ]
    })
})
```

`allow_partial_outputs: true` 使结构端口不足以容纳所有输出时，**多余的输出会被丢弃，而不是让配方失败**。详见 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema)。

这条配方有 3 个物品输出（煤、木炭、20% 概率的火药），还要求 `min_stage: 2`，因此一段结构不能启动它。产物能否接收由输出总线的槽位、容量、过滤与规划结果决定；一个多槽总线可能容纳多种产物，不能把“输出条目数”直接等同“输出端口数”。

`mmcr:stage` 需求的 `io` 默认为 input，只接受 input；`min_stage` 为 1～64 的整数，要求当前阶段至少达到该值。编程式对应为 `api.stageRequirement(int)` 或 `MachineRecipeBuilderJS.requiresStage(int)`。此提交的 RecipeSchema 没有同名 `requiresStage` 链式函数，`event.custom` 直接写 JSON 条目即可。

其他字段含义详见 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema)。

数据驱动的配方支持热加载，修改后 `/reload` 即可。

## 特殊机制：端口族并集与分组结构

### 端口族并集

参见 [KubeJSApi.anyOfItemInput](../API/KubeJS#kubejsapi) / [KubeJSApi.anyOfEnergyInput](../API/KubeJS#kubejsapi) / [KubeJSApi.anyOf](../API/KubeJS#kubejsapi)：

```javascript
.set('C', api.anyOf(
    api.anyOfItemInput(),
    api.anyOfItemOutput(),
    api.anyOfEnergyInput(),
    api.block('minecraft:deepslate_bricks')
))
```

C 字符被绑定到 4 个候选的并集：3 类端口再加一块深板岩砖。这意味着玩家在 C 位置可以摆"任意等级 / 任意类型的物品输入端口、物品输出端口、能量输入端口或装饰深板岩砖"，结构都能成型。

并集谓词是 MMCR 端最常用的"端口族匹配"工具。它的好处在于：

- **解耦**：结构不需要关心具体某个等级或某个厂商的端口叫什么 ID。`anyOfItemInput()` 自动包含**当前注册表中所有等级的物品输入端口**。
- **灵活**：玩家在摆端口时有充分的自由度。
- **可读**：相比逐一用 `api.block(...)` 枚举具体端口方块，`api.anyOfItemInput()` 写起来短得多。这里的 `KubeJSApi` 没有 `port(String)` 方法。

### 为什么要分组（`mainStructure` + `expandStructure`）

回到本机器的核心问题。同一台"蒸馏塔"机器，玩家可以搭 1 段、2 段或 3 段，配方还能根据段数给出不同产物。

如果只用扁平式 API 写一个固定大小的结构，玩家就必须搭满所有段。这违背了"按需扩张"的设计目标。

分组结构的工作方式：

1. **`.mainStructure(stage => ...)`** 声明阶段 1 的完整结构。
2. **每个 `.expandStructure(stage => ...)`** 声明下一个阶段的**完整结构**，每份都有自己的模式、字符、端口和控制器。本例阶段 2 / 3 的模式整体高度增加，不能只传新增一层。
3. **运行时**：从较高阶段向较低阶段尝试完整形态，选中匹配的阶段。真正的增量声明方法是 `.extension(stage => ...)`，其 `EXTENSION` 模式会合并到前一阶段，重叠坐标若定义冲突则拒绝；本例没有使用它。

阶段式 API 的完整列表见 [MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs)。

`mainStructure` 必须先调用且只能调用一次，`expandStructure` 声明后续形态。两者的 JS 签名都是 `Consumer<MachineStructureStageBuilderJS>`：回调负责修改 stage，返回值被忽略，表达式链或 `{ stage.pattern(...); ... }` 都有效。外层 `structure.build()` 返回 `void`。不能与顶层 `.pattern(...)` / `.set(...)` / `.controller(...)` 混用。

### `allow_partial_outputs` 与分组结构的协作

`allow_partial_outputs` 默认 false，输出策略是 `REQUIRE_FULL`；启用后为 `ALLOW_PARTIAL`，允许实际容量不能完全接收时输出部分产物，未接收的部分丢弃。它不放宽物品输入、能量输入或阶段门槛。

本例三个完整阶段分别有 1 / 2 / 3 个 `C` 端口候选位，但每个位还可能被选为输入、输出、能量输入或外壳。第一阶段不能满足 `min_stage: 2`；第二阶段即使满足阶段门槛，也可能因没有足够的输入与能量端口而不能运行。阶段号不等于有效输出容量。

实际教学搭建可用第三阶段的三个 `C` 分别放物品输入、物品输出、能量输入，输出总线选足够槽位与容量。要设计“每段固定一种产物”，需额外建立端口标签或过滤约束，当前示例没有这种一段一产物的路由定义。

RecipeSchema 提供无参 `.allowPartialOutputs()`，向 JSON 写入 true；独立 `MachineRecipeBuilderJS` 则同时提供 `allowPartialOutputs()` 和 `allowPartialOutputs(boolean)`。不要把这两套调用表混为一谈。

## 小结

1. **`.expandableStructure(true)`** 让一台机器 ID 对应一组形态而不是单一结构。
2. **`.mainStructure(...)` + `.expandStructure(...)` × N** 让玩家按需扩张。
3. **`mmcr:stage`** 限制最低结构阶段，**`allow_partial_outputs`** 控制输出不足时的策略；两者职责不同。
