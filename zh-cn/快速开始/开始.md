## 写在最前

本 Wiki 以 Minecraft **`26.1.2`** 的 MMCR 为基准，示例和 API 参考对照源码提交 [`f234477b`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/tree/f234477b)。Java 开发环境使用 **Java 25**；KubeJS 示例对应 **`26.1.2-8.0.6`**。开发附属 Mod 时，请使用 `cn.howxu.mmcr.publicapi` 下的公共接口；脚本通过 `MMCR` 和 `MMCREvents` 访问 KubeJS 集成层，两者的底层类型并不相同。

## 开始前的准备

在开始前，你需要知道这样一个事实: 高版本的Minecraft使用了一种叫做 `数据驱动` 的策略，这个策略的详细情况你可以自己到搜索引擎上查，其核心为 **把"可变的东西"全部外置成数据，源码只提供机制(mechanism)，不写具体内容(content)**。

这就间接导致了 MMCE 的使用 JSON 文件直接加载多方块结构机械的策略失效了。因为 MMCR 使用 **单个机械结构拥有独立控制器方块** 的策略，想用 JSON 组织机械结构，就必须**在 Minecraft 进入数据文件扫描前，提前扫完 MMCR 有关的 JSON 文件并据此生成方块**。然而这涉及生命周期问题，相当复杂。

另一种曾经被考量的思路是单独抽离一个 JSON 扫描策略，即主动扫描 MMCR 定义的目录中的 JSON 文件。这样生命周期问题就解决了，但是需要自己写 JSON 解析、重新寻找合适的扫描时机、组织结构、序列化、同步等等。工作量可能比研究生命周期问题更大。

因此，MMCR 现在采取的策略是: **同时提供 `Java API` 与 `KubeJS 集成`**。**Java API** 是在所有情况下都可以使用的、功能最为丰富的 API。**KubeJS 集成** 则是面向更多整合包作者以及普通玩家的 API。

## 1. 选择你的 API

- **Java API**: 使用 MMCR 提供的公共 API，通过订阅 MMCR 提供的事件，编写 Java 代码来向游戏添加你的机械、结构、配方、自定义 Tick、自定义 Render 等等。
- **KubeJS集成**: MMCR 提供完整的 KubeJS 集成，你可以通过 KubeJS 脚本，在正确的时机调用 MMCR 提供的函数和事件，进而向游戏添加你的机械、结构、配方、自定义 Tick 等等。

## 2. 我应该使用哪种 API

实际上两种 API 各有优劣:

对于`KubeJS 集成`:

- 门槛较低，只需要基础的 KubeJS 使用经验即可快速上手
- 提供**结构和配方**的`热重载`功能，意味着可以在游戏中快速调试结构和配方

- 必须安装 KubeJS 模组
- KubeJS 使用非标准的 JavaScript 语言，意味着在多数 IDE 中没有智能提示，并且代码调试难度较高
- 无法使用 MMCR 的自定义 Render 功能，这个功能由 Java API 独占
- 自定义 Tick 可以使用脚本回调，但调用世界操作或底层 Java 类型时，需要了解对应的 Minecraft API 和 Rhino 类型转换，总体上来说吃力不讨好

对于`Java API`:

- 拥有最全面的 API 体系架构，原生支持，只需安装 MMCR
- 可以直接接入你的 Mod 开发，意味着你可以使用 IDEA 的智能提示和调试功能
- 拥有自定义 Render 功能，可以写出更强大的自定义 Tick

- 门槛较高，需要有一定 Mod 开发经验的开发者使用
- 无法热重载配方和结构，意味着你必须重启游戏才能看到结构和配方修改后的效果

事实上，你完全可以将 KubeJS 集成和 Java API 联合在一起使用：用 Java API 写机械定义、自定义 Tick 和 Render，用 KubeJS 做结构和配方的热重载。

完全消除二者的劣势是一个涉及同步和生命周期的复杂问题，几乎不可能办到，因此当前的设计是多方妥协下的最优处理。

## 3. 了解生命周期

接下来，你需要了解 MMCR 对待外部 API 的生命周期。机器定义必须在控制器注册前收集；结构在控制器可用后收集；Java 静态配方在物品组件绑定后收集。这些 Java 注册事件都属于启动流程，虽然它们发布于 `NeoForge.EVENT_BUS`，并不等于服务器运行期事件。

可以把内容声明流程概括为:

> **Mod 启动 → 机器定义 → 结构和配方 → 提交**

KubeJS 则分别使用 `startup_scripts` 声明机器定义，使用 `server_scripts` 声明可重载结构和配方。启动声明需要重启游戏；服务端声明可通过 `/reload` 重新加载。

其中，**机器定义**和**结构与配方**就是我们需要关注的两个阶段。在这两个阶段发生了最重要的两件事情：**注册机器定义**和**加载结构与配方**。

正是在这两个阶段里，**无法在运行期改变**的内容和**可以改变**的内容出现了分叉。

## 4. 无法在运行期改变的内容

简单而言，就是不重启游戏删不掉、改不了的内容。

因为每台机器都具有启动时注册的控制器方块，因此**机器定义**无法通过普通 `/reload` 改变。这里的定义指机器身份、控制器和行为配置，不是结构的方块布局；KubeJS 声明的结构布局可以重载。同时不可改变的还有:

- 自定义 Tick: 在启动期绑定到机器定义
- 机器基础外观: 涉及复杂的同步问题
- 运行音效: 涉及注册问题
- 配方池: 涉及注册和同步问题
- Modifier 定义: 涉及注册问题
- Level 定义: 涉及注册问题

实际上，只要是 MMCR 在 KubeJS `startup` 阶段声明或注册的内容，都是无法改变的内容。

对于 Java API 而言，其所有内容都必须重新编译才能生效。

## 5. 可以在运行期改变的内容

即 KubeJS 支持热重载的内容。得益于高版本 Minecraft 的数据驱动策略， MMCR 只需要提供良好的序列化和同步策略就可以实现结构和配方的热重载。简单而言，凡 MMCR 在 KubeJS `server` 阶段声明或注册的内容，都是可以在运行时改变的。

对于 Java API 而言，其所有内容都必须重新编译才能生效。

## 6. 为什么需要了解生命周期

生命周期的存在使每个阶段`应该做什么`和`不应该做什么`变得清晰，督促开发者写出易于理解和清晰的代码，同时可以规范运行时的注册加载流程，进而避免了因为混乱的生命周期导致不可预料的**ERROR**，也是 MMCR 追求的现代 API 设计的一部分。

简单地说，就是为了防止开发者做出在**结构与配方**期间注册**机器定义**这种事情，然后游戏崩溃了，控制器方块找不到，结构和配方在 JEI 里翻不出来，最后日志还看不懂。
