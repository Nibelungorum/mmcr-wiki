# 算力-网络交互示例 — KubeJS 网络通信机器

本文是 KubeJS 进阶示例的第二篇。

行为回调使用底层 `api.machine.definition.TickBehaviorContext` / `MachineIoPlan`，网络入口使用 `api.network` 的引用与请求类型。`ctx.dataStorage()` 返回 `api.data.view.DataStorage`；请求处理回调的存储参数则是底层 `api.data.DataStorage`，不要把它们替换成 Java `publicapi` 的类型。

本文对官方脚本的三处 PRODUCER 存储写入作了签名适配：直接传入布尔值 / 数字，而不是传 `api.dataValue(...)`。后者生成底层数据值，不被 tick 存储视图的 `Object` 重载接受。CENTER 请求处理器收到底层存储，继续使用 `api.dataValue(reported)`。

与 [数据存储测试机器](./数据存储测试机器) 不同，本教程**同时注册两台机器**：一台 PRODUCER（生产者）和一台 CENTER（中心），演示每 tick 检查 FE、每 20 tick 条件上报、中心每 tick 聚合。

## 机器

算力-网络交互示例 一次注册两台机器：

1. **PRODUCER（生产者，`kubejs_network_producer_machine`）**：
   - 每 tick 检查是否有 FE 输入。
   - 每 20 tick 检查是否有水输入。
   - 根据输入状态计算"算力"（power，单位 `tfps`）。
   - **每 20 tick 在 FE 提交成功等条件满足时把算力推到 CENTER**，通过 [`api.sendRequest`](../API/KubeJS#sendrequestnetworkinterfacereference-source-machinereference-target-string-requestid-object-body--void)。
   - 控制器屏幕显示算力、水源状态、FE 状态。
   - 有 FE 时，每次 20 tick 检查若取水失败，干燥计数加 1；达到 30 后会**爆炸**。这是按游戏 tick 推进，不保证真实时间 30 秒。

2. **CENTER（中心，`kubejs_network_center_machine`）**：
   - 注册 [`requestProcess(REPORT_POWER, ...)`](../API/KubeJS#requestprocessstring-requestid-requestprocess-process--machinebuilderjs) 回调，接收 PRODUCER 的算力上报，写到自己的 `DataStorage`，键名 `power_<peerHash>`（按节点哈希分桶，避免互相覆盖）。
   - 每 tick 跑 `serverTick`：尝试消耗 200 FE、收集连接记录、清理孤儿键、求和、写控制器UI文本和 Jade 文本。缺 FE 只改变提示，不阻止统计。

两台机器通过 [`networkInterface(maxCount, maxConnections)`](../API/KubeJS#networkinterfaceint-maxcount-int-maxconnections--machinebuilderjs) 声明网络能力，通过 [`allowNetworkMachine(...)`](../API/KubeJS#allownetworkmachinestring-machineid--machinebuilderjs) 互相加白名单。

MMCR 在两端都校验白名单，缺一不可。

## 网络通信模型图解

MMCR 提供入队发送与目标处理器派发；这份示例是**单向上报**，没有响应消息或成功确认回调：

```
PRODUCER → sendRequest → 服务端队列 → CENTER.requestProcess
                       校验失败 → PRODUCER.requestFailed（需另行注册）
```

示例中演示的是 `producer → center` 单向推消息。下面是完整数据流：

```
  ┌─────────────────────────────────────────────────
  │                  PRODUCER                       
  │                                                 
  │  Tick:                                          
  │    1. try to consume FE                         
  │    2. every 20 ticks consume wster              
  │    3. upodate data to DataStorage               
  │    4. 20 tick -> KubeJSApi.sendRequest          
  │       → REPORT_POWER                            
  │       → body: { "power": <Recent Power> }       
  │       → target: iface.connections().get(0)      
  └─────────────────────────────────────────────────
                       │
                       │  RequestBody("power" → 20.0)
                       │
                       ▼ 
  ┌─────────────────────────────────────────────────
  │                   CENTER                        
  │                                                 
  │  requestProcess(REPORT_POWER, (body, request,   
  │      senderStorage, receiverStorage) => {       
  │    receiverStorage.set(                         
  │      "power_" + request.peer().hash(),          
  │      api.dataValue(body.get("power")            
  │        .flatMap(v => v.asDouble())              
  │        .orElse(0))                              
  │    );                                           
  │  });                                            
  │                                                 
  │  serverTick:                                    
  │    1. FE consume                                
  │    2. liveCount = iface.connections().size()    
  │    3. collect connectedHashes                   
  │    4. delete offline connections                
  │    5. summary power_*                           
  │    6. UI update                                 
  └─────────────────────────────────────────────────
```

要点：

- **生产者不直接编码中心坐标**
    它只调用 `iface.connections().get(0)` 拿到第一个连接，由 MMCR 内部根据网络接口的拓扑把请求转过去。
- **请求体是键值映射**，值都是 [`api.dataValue(...)`](../API/KubeJS#datavalueobject-value--datavalue) 支持的类型,以保持类型安全。
    源码里 body 用普通 JS 对象 `{ power: powerPublished }`，MMCR 会把它自动包装成 `DataValue`。
- 中心收到后通过 [`requestProcess`](../API/KubeJS#requestprocessstring-requestid-requestprocess-process--machinebuilderjs) 回调处理。处理逻辑完全由中心机器定义，生产者不关心。
- **入队不代表处理成功**：目标不在源接口连接表时，`sendRequest` 直接抛 `IllegalArgumentException`；请求体不是映射或值不能转换时也可能在入队前失败。派发阶段的白名单、区块、结构、连接与处理器校验失败会调用可用的 `requestFailed(...)` 处理器。本例没有注册失败处理器，也没有自动重试。
- 目标处理器抛 `RuntimeException` 时，派发器记录日志；当前实现不会因此调用 `requestFailed`，也不会回滚处理器已执行的普通数据写入。

## 机器定义详解

[`A_Network_Machine.js`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/startup_scripts/advance/A_Network_Machine.js)，常量声明：

```javascript
MMCREvents.startup(event => {
    const api = MMCR.getAPI()
    const RecipeIO = api.recipeIO()

    const ExplosionInteraction = Java.loadClass("net.minecraft.world.level.Level$ExplosionInteraction")

    const PRODUCER_ID = "mmcr_kubejs:kubejs_network_producer_machine"
    const CENTER_ID = "mmcr_kubejs:kubejs_network_center_machine"
    const REPORT_POWER = "mmcr_kubejs:report_power"

    const waterRequirement = api.fluidInputRequirement("minecraft:water", 100)
    // ...
})
```

- `RecipeIO`、`api` 是别名。
- `ExplosionInteraction` 是 Mojang 的内部枚举，`level.explode(...)` 用 `BLOCK` / `MOB` / `NONE` 区分爆炸的破坏方式。
- 字符串常量：`PRODUCER_ID` / `CENTER_ID` 是机器注册 ID，`REPORT_POWER` 是网络请求 ID。
- `waterRequirement` 提前构造一次"100 mB 水输入"需求，避免在 tick 回调里反复创建。

### PRODUCER 的机器定义

```javascript
const machine_producer = event
    .createMachine(PRODUCER_ID)
    .recipePool(PRODUCER_ID)
    .displayNameKey("machine.mmcr_kubejs.kubejs_network_producer_machine")
    .appearance("minecraft:white_wool")
    .networkInterface(1, 1) // allow 1 network port and max 1 connections
    .allowNetworkMachine(CENTER_ID) // allow connect to network center machine
```

四个声明 + 两个网络能力：

- `.displayNameKey(...)`：本地化键。
- `.appearance("minecraft:white_wool")`：不赘述。
- [`.networkInterface(1, 1)`](../API/KubeJS#networkinterfaceint-maxcount-int-maxconnections--machinebuilderjs)：声明这台机器最多拥有 1 个网络接口，活跃接口的连接记录总数最多为 1。
- [`.allowNetworkMachine(CENTER_ID)`](../API/KubeJS#allownetworkmachinestring-machineid--machinebuilderjs)：白名单，只允许与 `CENTER_ID` 通信。
**双向校验**：另一端 CENTER 也必须把 `PRODUCER_ID` 写进自己的白名单。

### CENTER 的机器定义

```javascript
const machine_center = event
    .createMachine(CENTER_ID)
    .recipePool(CENTER_ID)
    .displayNameKey("machine.mmcr_kubejs.kubejs_network_center_machine")
    .appearance("minecraft:black_wool")
    .networkInterface(1, 16) // one interface but 16 connections
    .allowNetworkMachine(PRODUCER_ID)
    // register a request process for REPORT_POWER id
    .requestProcess(REPORT_POWER, (body, request, senderStorage, receiverStorage) => {
        if (receiverStorage == null) return
        // the power value that producer produced(what a sentence)
        let reported = Number(body.get("power").flatMap(v => v.asDouble()).orElse(0))
        // 按来源哈希分桶；哈希不保证无碰撞
        let key = "power_" + request.peer().hash()
        receiverStorage.set(key, api.dataValue(reported))
    })
```

关键点：

- [`.networkInterface(1, 16)`](../API/KubeJS#networkinterfaceint-maxcount-int-maxconnections--machinebuilderjs)：最多 1 个接口，机器活跃接口的连接记录总数最多为 16。
- [`.allowNetworkMachine(PRODUCER_ID)`](../API/KubeJS#allownetworkmachinestring-machineid--machinebuilderjs)：白名单对应。
- [`.requestProcess(REPORT_POWER, ...)`](../API/KubeJS#requestprocessstring-requestid-requestprocess-process--machinebuilderjs)：注册请求处理器。
`REPORT_POWER` 是与 PRODUCER 端约定的请求 ID。
第二个参数是4参数回调 `(body, request, senderStorage, receiverStorage)`。

处理器内部逻辑：

1. `if (receiverStorage == null) return`，CENTER 没有关联数据存储时直接放弃；目标结构未成型会在派发校验阶段失败，不会进入处理器。
2. `body.get("power").flatMap(v => v.asDouble()).orElse(0)` 从 `RequestBody` 取 `power` 字段，用 `asDouble()` 安全转换成 `Optional<Double>`，再 `Number(...)` 转回 JS 数字默认 `0`。
3. `request.peer().hash()` 拿到 PRODUCER 引用的哈希，用于本例分桶；不是全局唯一 UUID。
4. `receiverStorage.set(key, api.dataValue(reported))` 把这个 PRODUCER 的算力写到 CENTER 的 `DataStorage`，键名 `power_<hash>`。

:::info 相关信息
**`request.peer()` 的语义**：目标的请求处理器收到发送者的 `MachineReference(Identifier type, long hash)`；源端失败回调中的 peer 则是目标引用。哈希由维度 ID、机器类型 ID 和控制器坐标计算，仅在这些输入不变且算法不变时可重复得到。`power_<hash>` 分桶不防理论上的哈希碰撞。
:::

最后两台机器各自 `.register()` 提交到当前注册窗口。

## 网络请求

完整 tick 行为有 5 段：能量 → 水 + 算力计算 → 干燥超限爆炸 → 网络上报 → 屏幕文本。

### 1. 能量

```javascript
let storage = ctx.dataStorage()
if (storage == null) return

let power = Number(storage.get("power").flatMap(v => v.asDouble()).orElse(0))
let dry_sec = Number(storage.get("dry_sec").flatMap(v => v.asDouble()).orElse(0))
let feOk = true

let energyPlan = ctx.ioPlan()
energyPlan.addInput(api.energyRequirement(RecipeIO.INPUT, 100))
let energySim = energyPlan.simulate()
if (!energySim.energySatisfied() || !energyPlan.commit().successful()) {
    feOk = false
}
// 非检查帧保留已存状态；检查帧缺电时不取水、不增加干燥计数、不上报
let powerPublished = power
let dryPublished = dry_sec
let shouldReport = false
```

每 tick 尝试消耗 100 FE。`simulate()` 缓存规划，`commit()` 执行该规划且消费 plan。提交不自动模拟，模拟不预留资源，实际成功仍要看 `successful()`。这份纯能量计划可用 `energySatisfied()` 判断能量规划。

如果失败，`feOk = false`。非 20 tick 检查帧保留已存状态；到检查帧仍会模拟水并写状态，但不会提交取水、不会增加干燥计数，也不会上报。脚本注释“缺电跳过所有下游更新”比实际实现更强，不能照此解释。

`storage.get("power").flatMap(v => v.asDouble()).orElse(0)` 是 MMCR 数据层最常见的读法，从 `DataValue` 取出 `double`，类型不对时退到 `0`。

`Number(...)` 是把 JS 自动转换出来的数值再变回 JS `number` 类型。

### 2. 水消耗 + 算力计算

```javascript
if (ctx.isDue(20)) {
    let waterPlan = ctx.ioPlan()
    waterPlan.addInput(waterRequirement)
    let waterSim = waterPlan.simulate()
    let hasWater = waterSim.inputsSatisfied()

    if (feOk && hasWater && waterPlan.commit().successful()) {
        power = 20
        dry_sec = 0
    } else {
        power = 10
        if (feOk) {
            dry_sec = dry_sec + 1
            hasWater = false
        }
    }

    storage.set("has_water", hasWater)
    storage.set("power", power)
    storage.set("dry_sec", dry_sec)
    powerPublished = power
    dryPublished = dry_sec

    if (dry_sec >= 30) {
        // ... 爆炸，见下节
    }

    shouldReport = feOk
}
```

`waterRequirement` 在启动回调中构造一次，表示 100 mB 水输入。每轮只创建新的 plan；`addInput` 会复制需求，复用需求声明不等于复用已消费的 plan。

有 FE 且成功取水 → `power = 20`、干燥计数清零。有 FE 但模拟或提交取水失败 → `power = 10`、干燥计数 +1、`hasWater = false`。缺 FE → `power = 10`、干燥计数不变，`hasWater` 仍是水模拟结果（即使有水也未消费）。三个键用普通 `set` 写入，不与 FE / 水 IO 共用事务。

### 3. 干燥超限爆炸

```javascript
if (dry_sec >= 30) {
    let level = ctx.level()
    let pos = ctx.controllerPos()
    level.explode(
        null,
        pos.getX() + 0.5,
        pos.getY() + 0.5,
        pos.getZ() + 0.5,
        4.0,
        false,
        ExplosionInteraction.BLOCK
    )
    return
}
```

`ctx.controllerPos()` 返回控制器方块位置，`ctx.level()` 是服务端世界。`dry_sec >= 30` 时在检查帧调用 `level.explode(...)`，爆炸强度参数为 `4.0`，不是固定半径 4 的保证。`BLOCK` 选择方块交互模式；具体破坏受游戏机制影响。爆炸检查本身没有 `feOk` 条件，持久化计数已达阈值时即使缺电也会触发。爆炸不属于 IO 事务，之后直接返回，不上报也不刷新本帧文本。

### 4. 网络上报

```javascript
if (shouldReport) {
    let interfaces = api.networkInterfaces(ctx)
    let iface = interfaces != null && !interfaces.isEmpty() ? interfaces.get(0) : null
    if (iface != null) {
        let connections = iface.connections()
        let target = connections != null && !connections.isEmpty() ? connections.get(0) : null
        if (target != null) {
            api.sendRequest(iface, target, REPORT_POWER, {
                power: powerPublished
            })
        }
    }
}
```

[`api.networkInterfaces(ctx)`](../API/KubeJS#networkinterfacesmachinebehaviorcontext-context--listnetworkinterfacereference) 是网络通信的入口，返回当前机器所有活跃网络接口的 `NetworkInterfaceReference` 列表（按位置排序）。每一步安全检查：

1. `interfaces` 非空 → 取第一个接口 `iface`
2. `iface.connections()` 返回接口保存的连接记录对应的 `MachineReference` 列表，不保证每个目标此刻已加载、成型或可处理请求
3. 取第一个连接 `target`，调用 [`api.sendRequest(iface, target, REPORT_POWER, body)`](../API/KubeJS#sendrequestnetworkinterfacereference-source-machinereference-target-string-requestid-object-body--void)：
- `iface` 是源接口。
- `target` 是目标机器（**不是**目标接口）。
- `REPORT_POWER` 是请求 ID，字符串 `mmcr_kubejs:report_power`。
- `body` 是 JS 普通对象 `{ power: powerPublished }`，MMCR 会自动用 [`api.dataValue(...)`](../API/KubeJS#datavalueobject-value--datavalue) 把每个值包成 `DataValue`。

`sendRequest` 把请求入队；[SharedIoEvents](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/internal/event/SharedIoEvents.java) 在 `ServerTickEvent.Post` 调用 [`NetworkServerState.dispatch(...)`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/internal/network/NetworkServerState.java)，按每 tick 请求预算取出请求。同 tick 派发前入队的请求可能就在该 tick 末处理；积压时可能延后，也可能校验失败，不能承诺固定“下一个 tick”到达。

**生产者不需要阻塞等待响应**。

### 5. 控制器文本与 Jade

```javascript
let powerId = api.id("mmcr_kubejs:producer_power")
let waterId = api.id("mmcr_kubejs:producer_water")
let feId = api.id("mmcr_kubejs:producer_fe")
let hasWater = storage.get("has_water").flatMap(v => v.asBoolean()).orElse(false)

ctx.screenText().append(api.screenScope().OPERATION, waterId, Text.literal(
    hasWater
        ? "Water: OK"

ctx.screenText().append(api.screenScope().OPERATION, feId, Text.literal(
    feOk ? "Energy: OK" : "Energy: LOW"

```

`screenText()` 与 `jadeText()` 都是写"按 `lineId` 幂等覆盖"的句柄。

同 `lineId` 反复 `append` 会替换上一帧内容。

`storage.get("has_water").flatMap(v => v.asBoolean()).orElse(false)` 是从 `DataValue` 取布尔值的写法，`asBoolean()` 是 `asDouble` 之外的另一类取值方法。

## 请求处理详解（CENTER tick 行为）

完整 tick 行为：

```javascript
machine_center.tickBehavior(behavior => behavior
    .serverTick(ctx => {
        let storage = ctx.dataStorage()
        if (storage == null) return

        let feId = api.id("mmcr_kubejs:center_fe")

        let energyPlan = ctx.ioPlan()
        energyPlan.addInput(api.energyRequirement(RecipeIO.INPUT, 200))
        let energySim = energyPlan.simulate()
        let energyOk = energySim.energySatisfied() && energyPlan.commit().successful()
        // consume FE

        // Re-derive the live producer count every tick so the UI reflects the actual
        // network connections even when storage has not been refreshed recently.
        let liveCount = 0
        let connectedHashes = new Set()
        let interfaces = api.networkInterfaces(ctx)
        let iface = interfaces != null && !interfaces.isEmpty() ? interfaces.get(0) : null
        if (iface != null) {
            for (let target of iface.connections()) {
                liveCount = liveCount + 1
                connectedHashes.add(String(target.hash()))
            }
        }
        // Remove reports whose producer is no longer connected. Collect keys first
        // because removing while iterating the Java map is unsafe.
        let staleKeys = []
        if (iface != null) {
            for (let key of storage.values().keySet()) {
                let keyString = key.toString()
                if (keyString.startsWith("power_")
                        && !connectedHashes.has(keyString.substring("power_".length))) {
                    staleKeys.push(key)
                }
            }
        }
        for (let key of staleKeys) storage.remove(key)

        // compute all the powers
        let total = 0
        let valueIter = storage.values().entrySet().iterator()
        while (valueIter.hasNext()) {
            let entry = valueIter.next()
            let key = entry.getKey()
            let value = entry.getValue()
            if (key.toString().startsWith("power_")) {
                total = total + value.asDouble().orElse(0)
            }
        }

        // some information display
        let count = liveCount

        let powerId = api.id("mmcr_kubejs:center_power")
        let countId = api.id("mmcr_kubejs:center_count")

        ctx.screenText().append(api.screenScope().OPERATION, powerId, Text.literal("Total Power: " + total + " tfps"))
        ctx.screenText().append(api.screenScope().OPERATION, countId, Text.literal("Connected Devices: " + count))
        ctx.screenText().append(api.screenScope().OPERATION, feId, Text.literal(
            energyOk ? "Energy: OK" : "Energy: LOW"
        ))

        ctx.jadeText().append(powerId, Text.literal("Total Power: " + total + " tfps"))
        ctx.jadeText().append(countId, Text.literal("Connected Devices: " + count + " producers"))
    })
)
```

4 步：

1. **消耗能量**：每 tick 尝试消耗 200 FE；失败后仍继续清理、求和与显示。
2. **收集连接信息**：`liveCount` 是第一个接口连接记录的条数，不是可靠的在线生产者计数；`connectedHashes` 是这些记录的 `hash()` 字符串集合。
3. **清理过期键**：遍历 `DataStorage` 所有键，找出以 `power_` 开头、但对应 `<hash>` 已经不在 `connectedHashes` 中的。
这些是孤儿键，收集到 `staleKeys`，再统一 `remove`。
4. **求和 + 写屏幕**：把所有 `power_*` 值转成 double 后求和；无接口时不会清理旧键，旧值仍计入总和。已连接但缺电的生产者不再上报，中心也没有超时淘汰逻辑，故显示的是最近报告的合计，不是实时有效算力保证。

`ctx.dataStorage().values()` 返回不可修改快照，不是实时 Java Map；先收集键再删除的写法可保留，但不能把官方注释“迭代时删除一定不安全”当作此视图的实际语义。普通 `remove` 立即生效。

## 特殊机制

视图 `asDouble()` 只读取实际为 `Double` 的值，不是任意数值转换器；若协议改用其他数值类型，读取方式也要相应调整。

`maxConnections` 在底层按这台机器活跃接口的连接记录总数校验，不是给每个接口单独一份额度；本例两台机器都只有一个接口。连接建立与派发都进行双向白名单校验，见 [NetworkInterfaceBindingCoordinator](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/internal/multiblock/NetworkInterfaceBindingCoordinator.java)。

### 白名单双向校验

[`networkInterface(maxCount, maxConnections)`](../API/KubeJS#networkinterfaceint-maxcount-int-maxconnections--machinebuilderjs) 只描述"我能做接口"，真正决定"我能和谁通信"的是 [`allowNetworkMachine(machineId)`](../API/KubeJS#allownetworkmachinestring-machineid--machinebuilderjs)。

MMCR 在两端都校验：

- PRODUCER 端 `allowNetworkMachine(CENTER_ID)` → 允许它主动连中心。
- CENTER 端 `allowNetworkMachine(PRODUCER_ID)` → 允许它被动接生产者。

任意一方缺失，物理连接都不会建立。

### `DataStorage` 作为网络协议的暂存

`power` / `dry_sec` / `has_water` 存储机器内部状态；本例只把 `power` 作为请求体字段发送，另外两个键没有进入网络协议。

`DataStorage` 充当了"机器状态 ↔ 网络协议"之间的桥：

- tick 行为把 `power` 写到 `DataStorage`
- 满足上报条件时把最新 `power` 通过 `RequestBody` 发出去
- CENTER 机器收到后写到自己的 `DataStorage`，用 `power_<peerHash>` 做命名空间避免覆盖

这种"复用键名"的写法使网络协议与机器状态一一对应，不需要单独的 schema 文件。

### 接口位置稳定性

`NetworkInterfaceReference` 的 `position()` 返回当前接口方块的世界坐标。MMCR 通过这个位置查"接口方块的连接表"。

[`NetworkInterfaceBlockEntity`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/internal/tile/NetworkInterfaceBlockEntity.java) 把 owner、连接端点的维度 / 坐标、机器类型 / 哈希和序号写入存档。存档能恢复记录不等于目标始终可达；释放 owner 会清空连接，派发也不会强制加载目标区块。

### `shouldReport = feOk` 语义

只有到达 20 tick 检查帧、能量消耗成功、且没有先因爆炸返回时才上报。缺电只阻止新报告，不会通知中心删除旧报告，所以这一条件不是完整的健康检查协议。

需要实时有效算力时，应另行设计时间戳、有效期或离线通知；本示例没有实现这些协议。

### 哈希分桶

[`MachineControllerBlockEntity.machineReference()`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/internal/tile/MachineControllerBlockEntity.java) 调用 [`MachineReferenceHasher`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/internal/network/MachineReferenceHasher.java)，按维度 ID、机器类型 ID 和控制器坐标计算哈希。同版本同维度同位置同类型重新成型可得到相同结果；换维度、移动或换类型不应假定仍相同。64 位哈希也不保证无碰撞，不能宣称“拆装 / 跨维度永远不变”。

### `requestProcess` 事务边界

`requestProcess.process(...)` 不接收 `TransactionContext`。这意味着：

- 调用 `receiverStorage.set(...)` 是**立即生效**的普通 `set`（不走事务）。
- 如果你同时还在做 IO（比如 `plan.commit(transaction => { storage.set(...); })`），那么 IO 失败回滚不会撤销 `requestProcess` 里直接写的 `DataStorage`。

`requestProcess` 只写 `DataStorage` ，不做 IO，规避了这个问题。

把 IO 留给 `serverTick` 只是分离处理阶段，不会自动让“接收 + IO”原子化。若需 IO 与状态变更同提交，应在 tick 中建立新 plan、模拟后用 `commitData(tx => storage.set(..., tx))` 写事务感知状态；请求接收时已执行的普通写入仍不在这一事务内。

### 延迟删除

CENTER tick 中 `storage.remove(key)` 是 `DataStorage` 的非事务版本，立即生效，**不可回滚**。

当前 `api.data.view.DataStorage` 只有 `remove(String)`，没有事务删除重载。在 `commit` / `commitData` 回调内调用普通 `remove` 也不会自动加入 journal；普通 `set` 和世界操作同样不能据此承诺原子回滚。
