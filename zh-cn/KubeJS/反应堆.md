# A_BlockState_Machine — 反应堆（带方块状态的机器）

本文演示一台用方块状态（block state）精确描述结构的反应堆型机器。代码直接对应 `example/startup_scripts/A_BlockState_Machine.js`、`example/server_scripts/structure/A_BlockState_Machine.js` 与 `example/server_scripts/recipe/A_BlockState_Machine.js` 三个文件；这是 KubeJS 示例里**第一次**出现 `api.state(...)` 谓词和精确朝向的楼梯/玻璃形态。

## 概览

A_BlockState_Machine 与 [A_Simple_Machine](A_Simple_Machine) 的关键差异在于**结构匹配粒度**：

- A_Simple_Machine 用 `api.block(...)` 描述外壳——只要是该方块的任意状态都算匹配。
- A_BlockState_Machine 用 `api.state(...)` 精确指定方块的**全部属性值**——`facing`、`shape`、`waterlogged` 等必须一一对齐。

反应堆结构的形态是一台 9 层 × 8 行 × 130+ 列的"超长多方块"——内部有黑曜石玻璃幕墙、翡翠与青金石核心、上下两段楼梯桁架、能量输出端口等复杂部件；为了保证这些部件的朝向与拼合正确，结构脚本里几乎全部字符都用了 `api.state(...)` 而不是 `api.block(...)`。

代码直接对应 Java 内置 BLAST_FURNACE 的 KubeJS 化版本，但走的是完全不同的实现路线：BLASR_FURNACE 的结构小巧（3×3×3）且不要求精确状态，本文的反应堆大而挑剔。两篇可对照阅读：[Java 端 BLAST_FURNACE](../JavaAPI/BLAST_FURNACE) 与 [A_Simple_Machine](A_Simple_Machine)。

## 机器定义

打开 [A_BlockState_Machine.js（启动期）](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/startup_scripts/A_BlockState_Machine.js)：

```js
// Define a more complex machine that uses block states.
MMCREvents.startup(event => {

    const builder = event
        .createMachine("mmcr_kubejs:kubejs_reactor") // Create the machine definition.
        .displayNameKey("machine.mmcr_kubejs.kubejs_reactor") // Translation key for the display name.
        .recipeFamily("mmcr_kubejs:kubejs_reactor") // Bind the recipe family.
        .appearance("minecraft:blue_ice") // Set the controller's appearance block.

    builder.register()
    // See server_scripts/structure/A_BlockState_Machine.js for the block-state structure.
})
```

`MMCREvents.startup(event => {...})` 把事件对象传入回调，`event` 是 [MMCRStartupEventJS](../API/KubeJS#mmcrstartupeventjs)；`event.createMachine(...)` 返回 [MachineBuilderJS](../API/KubeJS#machinebuilderjs)。

四件事的链式调用：

- `.createMachine("mmcr_kubejs:kubejs_reactor")`：注册 ID。命名空间 `mmcr_kubejs` 是 KubeJS 示例专用，避免与内置机器 `mmcr:reactor` 冲突。
- `.displayNameKey("machine.mmcr_kubejs.kubejs_reactor")`：本地化键。详见 [MachineBuilderJS.displayNameKey](../API/KubeJS#machinebuilderjs)。
- `.recipeFamily("mmcr_kubejs:kubejs_reactor")`：配方系列 ID。这是一个**分类/展示用**属性，不是配方匹配用的机器 ID。详见 [MachineBuilderJS.recipeFamily](../API/KubeJS#machinebuilderjs)。把它显式写出来有助于在 WAILA / JEI 之类的机器归属页面把所有属于同一族的配方聚在一起。
- `.appearance("minecraft:blue_ice")`：把控制器的外观方块设为蓝冰。详见 [MachineBuilderJS.appearance](../API/KubeJS#machinebuilderjs)。这一步同时会自动派生出控制器底纹理与成型端口底纹理；本机器没有显式覆盖它们。

`builder.register()` 终结，把机器提交到启动期注册窗口。

> 备注：与 A_Simple_Machine 不同的是，这台机器没有 `.allowMultithreading()`、`.allowParallelism()`、`.maxParallelAmount(...)`。MMCR 默认多线程与并行都是关闭的——一台反应堆不需要并行控制器；它的结构非常挑剔，并行会让朝向判定变得不必要地复杂。

启动期窗口不可热加载。修改 `.js` 后必须重启游戏。

## 多方块结构

打开 [A_BlockState_Machine.js（结构阶段）](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/server_scripts/structure/A_BlockState_Machine.js)：

```js
MMCREvents.server(event => {
    const api = event.getAPI()
    const structure = event.createStructure("mmcr_kubejs:kubejs_reactor")

    structure
        .pattern("  ABBBD  ", "         ", "         ", "         ", "         ", "         ", "         ", "         ")
        .pattern(" AEXXXFD ", "   XXX   ", "         ", "         ", "         ", "         ", "         ", "         ")
        // …共 9 个 z 层，每层 8 个 y 行…
        .set('X', api.anyOf(
            api.anyOfItemInput(),
            api.anyOfItemOutput(),
            api.anyOfFluidOutput(),
            api.anyOfFluidInput(),
            api.anyOfEnergyOutput(), // This reactor can output energy without requiring an energy input port.
            api.block('minecraft:blue_ice')
        ))
        .set('A', api.state('minecraft:deepslate_brick_stairs[facing=east,half=bottom,shape=outer_right,waterlogged=false]'))
        .set('B', api.state('minecraft:deepslate_brick_stairs[facing=south,half=bottom,shape=straight,waterlogged=false]'))
        // …A~Z 与 a~c 共 30 个字符都用 api.state(...) 精确描述…
        .controller('C')
        .build()
})
```

`MMCREvents.server(event => {...})` 回调里的 `event` 是 [MMCRServerEventJS](../API/KubeJS#mmcrservereventjs)；`event.getAPI()` 返回 [KubeJSApi](../API/KubeJS#kubejsapi)，下文统一用 `api` 指代。`event.createStructure(...)` 返回 [MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs)。

与 [A_Simple_Machine](A_Simple_Machine) 相比，本机器的结构有两个**关键差异**：

1. **没有显式调用 `stateSensitive()`，但因为大量字符使用 `api.state(...)`，结构匹配本身就要求方块状态完全匹配**——见下面的「状态匹配与导出工具」一节。
2. **`X` 字符的并集特别宽**——包含 5 种端口和蓝冰：`anyOfItemInput`、`anyOfItemOutput`、`anyOfFluidOutput`、`anyOfFluidInput`、`anyOfEnergyOutput`、再加 `minecraft:blue_ice`。这是因为反应堆同一外壳方块位既允许端口，也允许作为"内部装饰"的蓝冰。能量输出特别标注了一行注释："This reactor can output energy without requiring an energy input port." —— 反应堆不依赖外部供电，所以结构里**只放能量输出端口、不放能量输入端口**。

`.controller('C')` 把 C 字符（位于第 7 z 层、第 2 y 行）标记为控制器位置。`.build()` 终结构建并提交。

> 备注：原文在文件末尾留了一段**导出工具相关的注释**：
>
> > Note: the export tool cannot determine the exact block state required by every block. For example, a stair without recorded state is exported as api.block(), which can cause mismatches. Replace it with the correct api.state() manually when necessary.
>
> 即 MMCR 的结构导出器在面对 `stairs` 等带状态方块时会丢失部分属性，导出的 `api.block(...)` 在运行时匹配会失败。必须**手动替换**为 `api.state(...)` 才能让结构真正成型。

## 配方

打开 [A_BlockState_Machine.js（配方阶段）](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/server_scripts/recipe/A_BlockState_Machine.js)：

```js
ServerEvents.recipes(event => {
    event.custom({
        type: 'mmcr:machine_recipe',
        machine: 'mmcr_kubejs:kubejs_reactor',
        tick_time: 300,
        requirements: [
            { type: 'minecraft:item', io: 'input', item: 'minecraft:apple', count: 3 },
            { type: 'minecraft:fluid', io: 'input', fluid: 'minecraft:water', amount: 1 },
            { type: 'minecraft:item', io: 'output', stack: { id: 'minecraft:diamond', count: 10 } },
            { type: 'minecraft:fluid', io: 'output', stack: { id: 'minecraft:lava', amount: 250 } },
            { type: 'neoforge:energy', io: 'output', fe_per_tick: 200 }
        ]
    })

    // This recipe cannot run because the structure has no energy input port.
    // The requirement and recipe systems are intentionally independent.
    event.custom({
        type: 'mmcr:machine_recipe',
        machine: 'mmcr_kubejs:kubejs_reactor',
        tick_time: 200,
        requirements: [
            { type: 'minecraft:item', io: 'input', item: 'minecraft:golden_apple', count: 2 },
            { type: 'minecraft:fluid', io: 'input', fluid: 'minecraft:water', amount: 800 },
            { type: 'minecraft:item', io: 'output', stack: { id: 'minecraft:gold_ingot', count: 2 } },
            { type: 'minecraft:fluid', io: 'output', stack: { id: 'minecraft:lava', amount: 450 } },
            { type: 'neoforge:energy', io: 'input', fe_per_tick: 10 },
            { type: 'neoforge:energy', io: 'output', fe_per_tick: 200 }
        ]
    })
})
```

两份配方展示了 `requirements` 系统与 `recipe` 系统的**有意分离**：

- 第一份只声明 `neoforge:energy` 的 **output** 方向——符合反应堆"对外输出能量"的设定。
- 第二份同时声明了 energy 的 **input** 与 output——但是结构里**没有任何能量输入端口**。这条配方在结构成型后仍能被加载、却**永远无法运行**（没有匹配的输入端口）。注释写道："The requirement and recipe systems are intentionally independent."——配方系统校验 JSON 结构是否合法，运行时系统才会去查端口。

字段含义详见 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema)。

数据驱动的配方支持热加载，修改后 `/reload` 即可。

## 特殊机制：`api.state(...)` 与 `api.block(...)` 的区别

这是 A_BlockState_Machine 与前面所有示例最大的不同点。

### `api.block(...)`：方块任意状态都算匹配

参见 [KubeJSApi.block](../API/KubeJS#kubejsapi)：

```javascript
const casing = api.block("minecraft:iron_block")
```

返回的 `BlockPredicate` 只比对**方块 ID**，无论方块是什么属性值都算匹配。这是 A_Simple_Machine 的写法——玩家在 4 个角位既可以放铁块任意形态（默认、被踩过的、被红石充能的），都不影响结构成型。

### `api.state(...)`：方块状态必须精确匹配

参见 [KubeJSApi.state](../API/KubeJS#kubejsapi)：

```javascript
const log = api.state("minecraft:oak_log[axis=x]")
```

返回的 `BlockPredicate` 同时比对**方块 ID 和所有属性键值对**。属性名未知、属性值无效或方块 ID 不存在都会抛 `IllegalArgumentException`。

A_BlockState_Machine 里大量使用 `api.state(...)`，原因是它的结构由楼梯、玻璃板、栅栏门等**带朝向/带连接状态**的方块组成。这些方块默认放置会有不同的 `facing`/`shape`/`waterlogged` 属性；要想让结构拼合正确，模式里每个字符都必须写出确切的状态值，例如：

```javascript
.set('A', api.state('minecraft:deepslate_brick_stairs[facing=east,half=bottom,shape=outer_right,waterlogged=false]'))
```

这行说的是："A 位置必须是一块朝东、底层、`outer_right` 形状、未浸水的深板岩砖楼梯。" 玩家摆放时也要用相同状态的楼梯，**任何其他状态都会导致结构失配**。

### `stateSensitive()` / `stateInsensitive()`：全局开关

[MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs) 还提供两个顶层方法：

| 方法 | 行为 |
| --- | --- |
| [`stateSensitive()`](../API/KubeJS#machinestructurebuilderjs) | 把整个结构设为状态敏感——所有用 `api.block(...)` 绑定的字符也升级为精确匹配该方块的默认状态。 |
| [`stateInsensitive()`](../API/KubeJS#machinestructurebuilderjs) | 把整个结构设为状态不敏感——所有用 `api.state(...)` 绑定的字符降级为只比对方块 ID。 |

A_BlockState_Machine 没有调用 `stateSensitive()`，因为它的结构几乎全部字符都用了 `api.state(...)`，**模式层已经强制状态匹配**。如果你想混合写法（部分用 `api.block(...)`、部分用 `api.state(...)`），就需要在结构开头显式调用 `stateSensitive()` 或 `stateInsensitive()` 来统一全局行为。

### 导出工具的局限

见上面「多方块结构」一节末尾的备注。MMCR 的导出器在导出 `stairs`/`slabs`/`walls` 等带连接状态的方块时，会退化为 `api.block(...)`。这意味着**首次导出后必须手动编辑**——把对应位置的 `api.block(...)` 替换为带正确属性的 `api.state(...)`。本文的反应堆文件里 A~Z、a~c 共 30 个 `api.state(...)` 字符，绝大多数都是为了修正导出器丢失的属性。

## 与其他教程的对比

### 对比 A_Simple_Machine

| 维度 | A_Simple_Machine | A_BlockState_Machine |
| --- | --- | --- |
| 结构尺寸 | 3 × 3 × 3 | 9 z 层 × 8 y 行 × 130 列 |
| 字符绑定 | 全部 `api.block(...)` | 几乎全部 `api.state(...)` |
| 端口并集宽度 | `'I'` 上 3 个并集（物品输入/输出、能量输入） | `'X'` 上 6 个并集（4 种 IO 端口 + 能量输出 + 蓝冰） |
| 控制器外观 | 由 `displayNameKey` 派生 | 显式 `.appearance("minecraft:blue_ice")` |
| 能量方向 | 配方 input | 配方 output（反应堆是发电机） |
| 配方策略 | 单条配方演示 | 两条配方演示"配方/结构有意分离" |

### 对比 Java 端 BLAST_FURNACE

Java 版的 [BLAST_FURNACE](../JavaAPI/BLAST_FURNACE) 结构是 3×3×3 的小巧高炉，用 `BlockPredicate.block(...)` 和 `InterfacePredicates.anyItemInput()` 等并集谓词拼装。它的模式层完全不关心方块的朝向或连接状态。

A_BlockState_Machine 走了相反的路线——结构很大、模式层关心每一个 `facing` 和 `shape` 属性。如果你的机器需要玩家精确摆放（比如现实版的反应堆、聚变堆、炼金塔），就照本例用 `api.state(...)`；如果只是普通的"冶炼/合成/搅拌"型机器，A_Simple_Machine 的写法完全够用。

## 小结

A_BlockState_Machine 演示了三件事：

1. **用 `api.state(...)` 精确控制结构匹配**——楼梯、玻璃、栅栏门等带状态方块必须按状态匹配，否则结构无法成型。
2. **`api.anyOf(...)` 把多种端口与外壳并集**——`X` 字符同时允许 4 种端口和蓝冰，让玩家在反应堆内部能灵活放置。
3. **配方系统与端口系统有意解耦**——配方可以声明任何方向的 energy 需求，运行时不匹配端口也不会让配方加载失败，但执行时会失败。

接下来可以阅读 [A_Group_Machine](A_Group_Machine) 看 `mainStructure` + `expandStructure` 的可扩展结构；或 [A_Vertical_Machine](A_Vertical_Machine) 看控制器朝向与旋转对称的开关。
