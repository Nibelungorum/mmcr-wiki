# A_Group_Machine — 蒸馏塔（可分组扩展的机器）

本文演示一台**可分组扩展**的蒸馏塔。蒸馏塔的"段数"可以根据配方的需求动态拼装：1 段、2 段、3 段都是同一台机器。代码直接对应 `example/startup_scripts/A_Group_Machine.js`、`example/server_scripts/structure/A_Group_Machine.js` 与 `example/server_scripts/recipe/A_Group_Machine.js` 三个文件。

## 概览

A_Group_Machine 与 [A_Simple_Machine](A_Simple_Machine) 的关键差异在于**结构形态**：

- A_Simple_Machine 用扁平式 `.pattern(...).set(...).controller(...).build()` 写一个**单一**结构。
- A_Group_Machine 用阶段式 `.mainStructure(...).expandStructure(...).expandStructure(...)` 写**一组**结构——玩家可以选择搭 1 段、2 段或 3 段，同一台机器的"等级"由此决定。

蒸馏塔是分组结构的经典场景：蒸馏每一级都需要独立的端口与外壳；如果只有 1 级，玩家就是"小型蒸馏塔"，3 级就是"大型蒸馏塔"。MMCR 用**端口族并集 + 结构阶段枚举**让一台机器 ID 同时覆盖多种形态。

`expandableStructure(true)` 是本机器在启动期的关键开关；它告诉 MMCR："这台机器的结构是一组阶段而不是单个结构。" 详见 [MachineBuilderJS.expandableStructure](../API/KubeJS#machinebuilderjs)。

## 机器定义

打开 [A_Group_Machine.js（启动期）](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/startup_scripts/A_Group_Machine.js)：

```js
// Register a machine with an expandable structure.

MMCREvents.startup(event => {

    const distillation_tower = event
        .createMachine("mmcr_kubejs:kubejs_distillation_tower")
        .displayNameKey("machine.mmcr_kubejs.kubejs_distillation_tower")
        .recipeFamily("mmcr_kubejs:kubejs_distillation_tower")
        .appearance("minecraft:polished_blackstone")
        .expandableStructure(true) // Enable the expandable structure.

    distillation_tower.register()

    // See server_scripts/structure/A_Group_Machine.js for the grouped structure.
})
```

`event.createMachine(...)` 返回 [MachineBuilderJS](../API/KubeJS#machinebuilderjs)。链式调用的四件事：

- `.createMachine("mmcr_kubejs:kubejs_distillation_tower")`：注册 ID `mmcr_kubejs:kubejs_distillation_tower`。
- `.displayNameKey(...)`：本地化键。
- `.recipeFamily(...)`：配方族 ID，与机器自身 ID 相同；显式写出便于 WAILA / JEI 聚类。详见 [MachineBuilderJS.recipeFamily](../API/KubeJS#machinebuilderjs)。
- `.appearance("minecraft:polished_blackstone")`：把控制器外观设为磨制黑石。详见 [MachineBuilderJS.appearance](../API/KubeJS#machinebuilderjs)。
- **`.expandableStructure(true)`**：声明这台机器的结构是分组（可扩展）结构。这是本机器与 [A_Simple_Machine](A_Simple_Machine) 的根本区别。详见 [MachineBuilderJS.expandableStructure](../API/KubeJS#machinebuilderjs)。开启后，结构阶段必须用 `.mainStructure(...)` + `.expandStructure(...)` 写法，而不是扁平式 `.pattern(...).set(...)`。

启动期窗口不可热加载，修改 `.js` 后必须重启游戏。

## 多方块结构

打开 [A_Group_Machine.js（结构阶段）](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/server_scripts/structure/A_Group_Machine.js)：

```js
MMCREvents.server(event => {
    const api = event.getAPI()
    const structure = event.createStructure("mmcr_kubejs:kubejs_distillation_tower")

    // Define the main structure of the distillation tower.
    structure
        // Use mainStructure to define the main section.
        .mainStructure(stage =>
            stage
                .pattern(['  XXX  ','  AAA  ','       ','       '])
                .pattern([' XXXXX ',' B   B ','  ACA  ','       '])
                .pattern(['XXXXXXX','A     A',' B   B ','  DDD  '])
                .pattern(['XXXXXXX','A     A',' B   B ','  DDD  '])
                .pattern(['XXXXXXX','A     A',' B   B ','  DDD  '])
                .pattern([' XXXXX ',' B   B ','  BBB  ','       '])
                .pattern(['  XXX  ','  BEB  ','       ','       '])
                .set('C', api.anyOf(
                    api.anyOfItemInput(),
                    api.anyOfItemOutput(),
                    api.anyOfEnergyInput(),
                    api.block('minecraft:deepslate_bricks')
                ))
                .set('X', api.block('minecraft:polished_blackstone'))
                .set('A', api.block('minecraft:deepslate_bricks'))
                .set('B', api.block('minecraft:polished_blackstone_bricks'))
                .set('D', api.block('minecraft:gilded_blackstone'))
                .controller('E')
        )
        // Use expandStructure to define an additional section.
        .expandStructure(stage => stage
            .pattern(['  XXX  ','  AAA  ','       ','       ','       '])
            .pattern([' XXXXX ',' B   B ','  ACA  ','  ACA  ','       '])
            // …同一字符定义、重复一次……
            .controller('E')
        )

        .expandStructure(stage => stage
            .pattern(['  XXX  ','  AAA  ','       ','       ','       ','       '])
            .pattern([' XXXXX ',' B   B ','  ACA  ','  ACA  ','  ACA  ','       '])
            // …同一字符定义、重复两次……
            .controller('E')
        )

        // Build the grouped structure.
        structure.build()
})
```

`MMCREvents.server(event => {...})` 回调里的 `event` 是 [MMCRServerEventJS](../API/KubeJS#mmcrservereventjs)；`event.getAPI()` 返回 [KubeJSApi](../API/KubeJS#kubejsapi)。

结构分三个阶段：

1. **`.mainStructure(stage => ...)`**：基础段。详见 [MachineStructureBuilderJS.mainStructure](../API/KubeJS#machinestructurebuilderjs)。每个阶段回调收到的 `stage` 是 [MachineStructureStageBuilderJS](../API/KubeJS#machinestructurestagebuilderjs)。这一段是 4 z 层 × 7 y 行 × 7 列 的塔身——控制器位于第 7 层。
2. **第一个 `.expandStructure(stage => ...)`**：扩展段 A。详见 [MachineStructureBuilderJS.expandStructure](../API/KubeJS#machinestructurestagebuilderjs)。同形状、同字符定义、但塔身多 1 z 层（5 z 层）。
3. **第二个 `.expandStructure(stage => ...)`**：扩展段 B。再加 1 z 层（6 z 层），中间的 `'A'` 段重复 3 次。

> 注意：原文 `structure.build()` 是在结构链式调用的**外层**调用——`structure.mainStructure(...).expandStructure(...).expandStructure(...)` 三段配置完后，回到 `structure` 上再 `.build()` 终结。展开形态 vs 主结构形态的"选择"在运行时由玩家摆放的方块数量自动决定。

每段内的字符定义完全相同：

- `'X'` → 磨制黑石（外壳）。
- `'A'` → 深板岩砖（内壁）。
- `'B'` → 磨制黑石砖（边框）。
- `'D'` → 镀金黑石（顶部装饰）。
- `'E'` → 控制器字符。
- `'C'` → `api.anyOf(...)` 联合谓词：物品输入端口 ∪ 物品输出端口 ∪ 能量输入端口 ∪ 深板岩砖。也就是说每一段中部允许玩家摆端口或装饰方块。

阶段式 API 与扁平式 API 不能混用——一旦调用 `.mainStructure(...)`，再调用扁平的 `.pattern(...)` / `.set(...)` 会抛 `IllegalStateException`。详见 [MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs) 的注意事项。

`.build()` 终结构建并提交。

## 配方

打开 [A_Group_Machine.js（配方阶段）](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/server_scripts/recipe/A_Group_Machine.js)：

```js
ServerEvents.recipes( event => {
    event.custom({
        type: 'mmcr:machine_recipe',
        machine: 'mmcr_kubejs:kubejs_distillation_tower',
        tick_time: 300,
        allow_partial_outputs: true, // Discard outputs when the structure lacks enough output ports.
        requirements: [
            { type: 'minecraft:item', io: 'input', item: '#minecraft:logs', count: 1 },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: { id: 'minecraft:coal', count: 3 }
            },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: { id: 'minecraft:charcoal', count: 4 }
            },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: { id: 'minecraft:gunpowder', count: 3 },
                chance: 0.2
            },
            { type: 'neoforge:energy', io: 'input', fe_per_tick: 20 }
        ]
    })
})
```

`allow_partial_outputs: true` 是这份配方的关键。详见 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema)。

注释写道："Discard outputs when the structure lacks enough output ports."——也就是当结构端口不足以容纳所有输出时，**多余的输出会被丢弃，而不是让配方失败**。

注释还指出："Without a three-level distillation tower, outputs without an available port are discarded." —— 这条配方有 3 个物品输出（煤、木炭、火药）；只有当玩家搭出**完整的 3 段蒸馏塔**时，3 种输出才都有端口可以落位；少搭一段的玩家在运行时会少出 1~2 种产物（剩余输出被丢弃）。

其他字段含义详见 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema)。

数据驱动的配方支持热加载，修改后 `/reload` 即可。

## 特殊机制：端口族并集与分组结构

### 端口族并集

参见 [KubeJSApi.anyOfItemInput](../API/KubeJS#kubejsapi) / [KubeJSApi.anyOfEnergyInput](../API/KubeJS#kubejsapi) / [KubeJSApi.anyOf](../API/KubeJS#kubejsapi)：

```javascript
.set('C', api.anyOf(
    api.anyOfItemInput(),
    api.anyOfItemOutput(),
    api.anyOfEnergyInput(),
    api.block('minecraft:deepslate_bricks')
))
```

C 字符被绑定到 4 个候选的并集——3 类端口再加一块深板岩砖。这意味着玩家在 C 位置可以摆"任意等级 / 任意类型的物品输入端口、物品输出端口、能量输入端口或装饰深板岩砖"，结构都能成型。

并集谓词是 MMCR 端最常用的"端口族匹配"工具。它的好处在于：

- **解耦**：结构不需要关心具体某个等级或某个厂商的端口叫什么 ID——`anyOfItemInput()` 自动包含**当前注册表中所有等级的物品输入端口**。
- **灵活**：玩家在摆端口时有充分的自由度。
- **可读**：相比 `anyOf(api.port("mmcr:item_input_bus_normal"), api.port("mmcr:item_input_bus_big"), ...)` 列举每个端口 ID，`api.anyOfItemInput()` 写起来短得多。

### 为什么要分组（`mainStructure` + `expandStructure`）

回到本机器的核心问题——同一台"蒸馏塔"机器，玩家可以搭 1 段、2 段或 3 段，配方还能根据段数给出不同产物。如果只用扁平式 API 写一个固定大小的结构，玩家就必须搭满所有段；这违背了"按需扩张"的设计目标。

分组结构的工作方式：

1. **`.mainStructure(stage => ...)`** 声明"最小可行结构"。1 段就是完整的蒸馏塔。
2. **每个 `.expandStructure(stage => ...)`** 声明一段**可选的扩展**。搭出 mainStructure 后**叠加** 1 段或 2 段，仍然是同一台机器。
3. **运行时**：MMCR 扫描世界里所有方块，匹配 mainStructure 或 mainStructure + N×expandStructure；只要匹配上一种形态，机器就算成型。

阶段式 API 的完整列表见 [MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs)。注意 `mainStructure` 只能调用一次，`expandStructure` 可以调用任意多次；两者都必须用回调式写法，不能与扁平式 `.pattern(...)` 混用。

### `allow_partial_outputs` 与分组结构的协作

回到配方里的 `allow_partial_outputs: true`。如果不开启这个字段，配方系统会要求结构里**所有输出条目都找到匹配端口**——3 段蒸馏塔有 3 个 `'C'` 位置可以放端口，3 个输出各得其所。如果玩家只搭 1 段（1 个 `'C'` 位置），多余 2 个输出找不到端口，配方在执行时会失败。

开启 `allow_partial_outputs: true` 后，**多余输出会被静默丢弃**，配方仍能跑完。这与分组结构形成了自然的配合：

- 玩家搭 1 段 → 最多 1 个输出端口 → 3 个输出里只有第 1 个产物能落位，火药、木炭丢弃。
- 玩家搭 2 段 → 最多 2 个输出端口 → 煤和木炭落位，火药丢弃。
- 玩家搭 3 段 → 3 个输出端口全开 → 煤、木炭、火药都落位。

详见 [MachineRecipeSchema.allowPartialOutputs](../API/KubeJS#machinerecipeschema) 函数式重载；JSON 字段形式 `allow_partial_outputs: true` 与 `event.custom(...).allowPartialOutputs()` 等价。

## 与其他教程的对比

### 对比 A_Simple_Machine

| 维度 | A_Simple_Machine | A_Group_Machine |
| --- | --- | --- |
| 结构形态 | 单一扁平结构 | 分组（1 个 main + N 个 expand） |
| 玩家可调形态 | 否 | 是（搭 1/2/3 段都是同一台机器） |
| 写法 | 扁平式 `.pattern().set().controller().build()` | 阶段式 `.mainStructure().expandStructure().build()` |
| 端口策略 | 中层固定 1 个 `'I'` 字符 | 每段中部 1 个 `'C'` 字符 |
| 配方策略 | 单配方、单输出 | 单配方、`allow_partial_outputs` 多输出 |

### 对比 A_BlockState_Machine

[A_BlockState_Machine](A_BlockState_Machine) 用 `api.state(...)` 精确匹配状态——它演示的是**单结构内的字符级精度**。A_Group_Machine 用 `expandableStructure(true)` + `expandStructure(...)` 演示的是**结构级可变性**。两者可以叠加：分组结构里的字符也可以用 `api.state(...)` 精确匹配。

## 小结

A_Group_Machine 演示了三件事：

1. **`.expandableStructure(true)`** 让一台机器 ID 对应一组形态而不是单一结构。
2. **`.mainStructure(...)` + `.expandStructure(...)` × N** 让玩家按需扩张。
3. **`allow_partial_outputs` + 多端口族并集** 让分组结构的"少搭少出"成为自然行为。
