# 怪物农场

怪物农场只有机器定义与结构，**没有注册配方或实体处理行为**。它用一个原木和铁栏杆笼子展示控制器竖直放置策略、方块标签匹配以及忽略位置。

## 概览

- `ControllerOptions` 同时声明允许竖直、非完全旋转对称、强制竖直三个选项。
- `BlockConditions.tag(BlockTags.LOGS)` 允许一组方块，而非某种固定木材。
- 未绑定的空格忽略世界中的对应位置，适合表达笼子中空区域。
- 可以合法注册没有配方的机器，但名称“怪物农场”并不会让它自动刷怪、杀怪或收集掉落物。

怪物农场不是内置示例中唯一配置朝向的机器：[裂化器](裂化器) 也允许竖直放置并声明完全旋转对称；本例更进一步要求控制器只能竖直放置。

## 机器定义

```java
private static final Identifier MONSTER_FARM = id("monster_farm");

public static void registerDefinitions(RegisterMachineDefinitionsEvent event) {
    if (!event.definitions().containsKey(MONSTER_FARM)) {
        MachineSpec machine = Machines
                .machine(MONSTER_FARM)
                .recipePool(MONSTER_FARM)
                .displayNameKey("machine.mmcr.monster_farm")
                .controller(c -> c
                        .id(MONSTER_FARM.withSuffix("_controller"))
                        .allowVerticalFacing(true)
                        .fullyRotationallySymmetric(false)
                        .requireVerticalFacing(true)
                )
                .build();
        event.registerMachine(machine);
    }
}
```

`id("monster_farm")` 展开为 `mmcr:monster_farm`。附属 mod 应使用自己的命名空间，例如 `Identifier.fromNamespaceAndPath("my_mod", "monster_farm")`。`recipePool(MONSTER_FARM)` 为机器声明池入口，但它不自动生成配方；池可以暂时没有规则。

`definitions().containsKey(...)` 防止重复注册同一机器 ID。`build()` 返回 `MachineSpec`，再由启动期事件提交。控制器 ID 为 `mmcr:monster_farm_controller`，与机器 ID 不同。

### 三个朝向选项

`controller(...)` 的签名是 `controller(Consumer<ControllerOptions>)`。回调直接配置库提供的选项；使用代码块时不返回配置对象。

| 选项 | 作用 | 本例意义 |
| --- | --- | --- |
| `allowVerticalFacing(true)` | 在水平四向之外允许朝上 / 朝下 | 显式开启竖直放置能力 |
| `fullyRotationallySymmetric(false)` | 不声明完全旋转对称的控制器表现 | 保留有方向的控制器表现 |
| `requireVerticalFacing(true)` | 要求竖直放置 | 排除水平四向 |

`requireVerticalFacing(true)` 会同时开启允许竖直，因此前面的 `allowVerticalFacing(true)` 是冗余但直观的声明。`fullyRotationallySymmetric(false)` 是默认值，源码将其显式写出。

不应从纹理选项推断结构绕过朝向检查。放置朝向影响模式到世界坐标的转换；竖直控制器还可能有水平滚转方向，不能把 `UP` / `DOWN` 两个 facing 值理解为只有两种完整世界变换。

## 完整结构

```java
@SubscribeEvent
public static void registerStructures(RegisterMachineStructuresEvent event) {
    if (!event.structures().containsKey(MONSTER_FARM)) {
        StructureSpec structure = Structures
                .structure()
                .fullStructure(s -> s
                        .pattern(p -> p
                                .layer("XXXXX", "XXXXX", "XXXXX", "XXXXX", "XXXXX")
                                .layer("ABBBA", "B   B", "B   B", "B   B", "ABBBA")
                                .layer("ABBBA", "B   B", "B   B", "B   B", "ABBBA")
                                .layer("ABBBA", "B   B", "B   B", "B   B", "ABBBA")
                                .layer("ABBBA", "B   B", "B   B", "B   B", "ABBBA")
                                .layer("XXXXX", "XXXXX", "XXDXX", "XXXXX", "XXXXX")
                                .where('X', any(tag(BlockTags.LOGS)))
                                .where('A', block(Blocks.OAK_LOG))
                                .where('B', block(Blocks.IRON_BARS))
                                .controller('D'))
                )
                .build(MONSTER_FARM);
        event.registerStructure(structure);
    }
}
```

`@EventBusSubscriber` 与 `@SubscribeEvent` 自动订阅游戏事件总线上的 `RegisterMachineStructuresEvent`，不需要手写 `bus.register(...)`。

### 切片形状与空格

六个切片，每个 5 行 × 5 列，模式是 5×5×6 的笼子：

```text
切片 0         切片 1..4      切片 5
XXXXX          ABBBA          XXXXX
XXXXX          B   B          XXXXX
XXXXX          B   B          XXDXX
XXXXX          B   B          XXXXX
XXXXX          ABBBA          XXXXX
```

两端是原木盖板，四个中间切片有橡木原木角柱、铁栏杆围边与中间 3×3 区域。内部共 36 个空格，未绑定条件，因此不要求空气，也不检查其中有什么方块或实体。这个忽略语义本身不构成“刷怪空间可用”的游戏逻辑检查。

所有切片的行数与行宽必须一致。世界朝向由控制器放置策略和模式变换决定，示意图显示的是本地坐标。

### 方块条件逐项说明

**`where('X', any(tag(BlockTags.LOGS)))`**

`tag(...)` 匹配原版原木标签，允许其中的木材与变体。`any(...)` 只有一个子条件时与该条件等价；以后可加其他候选块，但本例没有额外候选项。

**`where('A', block(Blocks.OAK_LOG))`**

角柱固定为橡木原木，`block(...)` 不限制 `axis=x/y/z`。若要强制指定状态，应使用 `state("minecraft:oak_log[axis=y]")` 并按需要开启 `stateSensitive()`，对照 [反应堆](反应堆)。

**`where('B', block(Blocks.IRON_BARS))`**

栏杆只约束方块类型，不要求特定连接状态。

**`controller('D')`**

没有手写 `where('D', ...)`，由模式构建阶段绑定本机器控制器。控制器字符需要在模式中出现一次，最终 `build(MONSTER_FARM)` 返回绑定到机器 ID 的 `StructureSpec`。

### 为什么没有接口

源码没有使用物品、流体、能量等接口条件，也没有 `portTiers(...)`。本例不接收材料、不产出物品，不需要加工 IO；[高炉](高炉) 则在 `I` 位置允许物品输入 / 输出与能量输入。

## 没有配方意味着什么

源码没有 `RegisterMachineRecipesEvent` 订阅方法，也没有注册 tick 行为。机器能用于展示结构和控制器，但不能仅凭笼子形状自动进入怪物处理流程。

要扩展成可工作的机器，可选择与目标行为匹配的方式：

1. **加工配方**：使用 `Recipes.recipe(...)` 创建 `RecipeDraft`，在 `RegisterMachineRecipesEvent` 中提交 `RecipeSpec`，并为结构增加所需接口。随机副产物可用 `outputChance(ItemStack, float)`，参考 [蒸馏塔](蒸馏塔)。
2. **世界行为**：用 `MachineDraft.tickBehavior(Consumer<TickHooks>)` 或 `preServerTick(Consumer<MachineContext>)` 配置与实体交互的回调，行为上下文与钩子均来自 `publicapi.behavior`。本文件没有提供这类实现。

这两条路解决不同问题；添加配方不会自动扫描实体，添加行为也要明确资源、掉落和运行条件。

## 与高炉对比

| 维度 | 高炉 | 怪物农场 |
| --- | --- | --- |
| 注册阶段 | 定义 + 结构 + 配方，另有客户端 JEI 工作站 | 定义 + 结构 |
| 控制器选项 | 使用默认声明 | 显式配置三个朝向选项 |
| 结构 | 3×3×3 | 5×5×6 |
| 忽略空格 | 1 格 | 36 格 |
| 接口 | 物品输入 / 输出、能量输入 | 无 |
| 端口等级 | 输入至少 `NORMAL` | 无 |
| 标签条件 | 无 | `tag(BlockTags.LOGS)` |
| 并行 / 多线程 | 声明启用 | 未启用 |
| 内置配方 | **2 条** | 0 条 |
