# 太空电梯 - 主机 + 模块

灵感来源于 GTL 的太空电梯。

本文演示 MMCR 的 **HOST + MODULE** 模式：一台"主机"大机器旁边挂一台"模块"小机器，模块的配方只在主机在场时才会跑。

## 机器简介

`A_Module_Machine` 由三个脚本文件组成，共定义一台电梯和一台重组机：

- `example/startup_scripts/A_Module_Machine.js`
- `example/server_scripts/structure/A_Module_Machine.js`
- `example/server_scripts/recipe/A_Module_Machine.js`

HOST 与 MODULE 之间的关系有三层：

1. **机器层**：主机通过 `.host(...)` 声明自己接受哪些模块。模块通过 `.module()` 标记自己可被主机接纳。
2. **结构层**：两台机器都用 `api.coupler()` 声明耦合器位置，并共享同一个世界坐标上的耦合器。仅相邻不构成连接；两台结构都要成型，主机要接受该模块，接口位置不能重叠。
3. **配方层**：模块必须有有效主机连接才能运行；`required_host_ids` 进一步限定连接的主机机器 ID。

未写 `required_host_ids` 的模块配方也不能脱离连接运行；省略名单只表示“任意有效连接的主机都可接受”。普通机器及 HOST 的运行状态不要求模块连接，因此名单不会成为普通主机的额外自匹配门槛。

## 机器定义

`startup_scripts/` 目录下的 [A_Module_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/startup_scripts/A_Module_Machine.js)：

```js
// Register a host machine and a module machine.
// This example is based on GTL's space elevator.

MMCREvents.startup(event => {
    const space_elevator = event
        .createMachine("mmcr_kubejs:kubejs_space_elevator")
        .displayNameKey("machine.mmcr_kubejs.kubejs_space_elevator")
        .recipePool("mmcr_kubejs:kubejs_space_elevator")
        .appearance('minecraft:smooth_quartz')
        .controllerBaseTexture('minecraft:block/quartz_block_bottom') // Smooth quartz has no standard texture, so set the base texture manually.
        .formedPortBaseTexture('minecraft:block/quartz_block_bottom')
        .host("mmcr_kubejs:kubejs_space_reassembler")

    const space_reassembler = event
        .createMachine("mmcr_kubejs:kubejs_space_reassembler")
        .displayNameKey("machine.mmcr_kubejs.kubejs_space_reassembler")
        .recipePool(
            "mmcr_kubejs:kubejs_space_reassembler",
            "mmcr_kubejs:kubejs_space_miner",
            "mmcr_kubejs:kubejs_space_1",
            "mmcr_kubejs:kubejs_space_2",
            "mmcr_kubejs:kubejs_space_3"
        )
        .appearance('minecraft:quartz_pillar')
        .allowMultithreading()
        .module()


    space_elevator.register()
    space_reassembler.register()
})
```

这个脚本里有两台机器在同一个 `MMCREvents.startup` 回调里注册。

脚本通常用 `.host(...)` 和 `.module()` 表达角色，也可用实际存在的 `.role('NORMAL'/'HOST'/'MODULE')` 字符串入口，不需要加载 Java 枚举。

### HOST

```js
const space_elevator = event
    .createMachine("mmcr_kubejs:kubejs_space_elevator")
    .displayNameKey("machine.mmcr_kubejs.kubejs_space_elevator")
    .recipePool("mmcr_kubejs:kubejs_space_elevator")
    .appearance('minecraft:smooth_quartz')
    .controllerBaseTexture('minecraft:block/quartz_block_bottom')
    .formedPortBaseTexture('minecraft:block/quartz_block_bottom')
    .host("mmcr_kubejs:kubejs_space_reassembler")
```

- `.displayNameKey(...)`：本地化键。
- `.recipePool(...)`：声明机器所属的有序配方池。机器可以加入多个配方池，每条配方仍只选择一个池。  
    详见 [API/KubeJS#recipePool](../API/KubeJS#recipepool-string-recipepoolids-%E2%86%92-machinebuilderjs)。
- `.appearance('minecraft:smooth_quartz')`：控制器的默认外观方块。
- `.controllerBaseTexture(...)` / `.formedPortBaseTexture(...)`：smooth_quartz 没有标准的方块纹理，需要手动指定 base 纹理。
- **`.host()`**：声明这台电梯接受 `kubejs_space_reassembler` 作为模块机器。  
    参数是变长 `String...`，可以一次声明多个模块。  
    详见 [API/KubeJS#machinebuilderjs](../API/KubeJS#machinebuilderjs)。

### MODULE

```js
const space_reassembler = event
    .createMachine("mmcr_kubejs:kubejs_space_reassembler")
    .displayNameKey("machine.mmcr_kubejs.kubejs_space_reassembler")
    .recipePool(
        "mmcr_kubejs:kubejs_space_reassembler",
        "mmcr_kubejs:kubejs_space_miner",
        "mmcr_kubejs:kubejs_space_1",
        "mmcr_kubejs:kubejs_space_2",
        "mmcr_kubejs:kubejs_space_3"
    )
    .appearance('minecraft:quartz_pillar')
    .allowMultithreading()
    .module()
```

`.module()` 是无参版本，等价于 `.module(true)`。

`.module()` 将机器标记为模块。显式角色与快捷方法不能矛盾：例如 `.role('NORMAL').module()`、`.role('HOST').module()` 会被拒绝；显式 HOST 还必须通过 `host(...)` 提供至少一个接受的模块 ID。模块不会仅因 `.module()` 自动获得主机连接。

`.host(...)` 除了设置 HOST 角色，还记录接受的模块 ID，不能仅用 `.role('HOST')` 代替；`.module()` 则是模块标记的便捷入口。

:::info 备注
KubeJS 端没有等价的 `.acceptedModule(...)` 命名。`.host(...)` 在内部就是 `acceptedModule(...)` 的别名。详见 [API/KubeJS#machinebuilderjs](../API/KubeJS#machinebuilderjs)。
:::

### 启动期不可热加载

机器定义必须重启游戏才能生效。

### 耦合器

电梯结构里有三个 `B` 字符，每个 `B` 都绑定到 `api.coupler()`：

```js
.set('B' ,api.coupler())
```

重组机结构里有一个 `E` 字符，也绑定到 `api.coupler()`：

```js
.set('E',api.coupler())
```

`api.coupler()` 返回 [`BlockPredicate`](../API/KubeJS#coupler--blockpredicate)，专门用来表示"机器耦合器"方块。

两套模式先各自成型，再通过**同一世界坐标的耦合器**建立连接。该坐标需要唯一可连接的主机与模块，且主机接受模块 ID、两台模式仍匹配、端口接口不重叠。共享耦合器不意味着共享物品、能量接口。

电梯的耦合器可以摆多个（每个 `B` 都是候选位置），重组机的耦合器只有一个（`E`）。

### 端口与控制器

电梯结构和 高炉 类似，`D` 槽位是物品输入 / 输出 / 能量输入的并集，方便在塔身任意方向接端口。

### 数据驱动配方的 `required_host_ids` 字段

```js
required_host_ids: [
    "mmcr_kubejs:kubejs_space_elevator"
]
```

这是数据驱动配方的顶层字段，对应 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema) 上的 `required_host_ids` 键。语义是把当前配方的"主机限定"列出来。

模块配方检查的是**当前有效连接的主机 ID**是否在名单内，不是搜索世界里是否有任意同 ID 主机成型。无连接时，即使附近另有成型电梯，配方也不能运行。

字段值为 ID 字符串数组，默认空集合；空集合对已连接模块不限制主机种类，但不解除模块必须连接的要求。普通机器 / HOST 的 `ModuleConnectionStatus` 为 `notRequired`，此字段不对其施加额外连接门槛；官方电梯配方也写了自己的 ID，本文保留该字段。

> 与 Java 端 `MachineRecipeBuilder.requiredHost(...)` 等价。KubeJS 数据驱动配方直接使用顶层字段。编程式 [`MachineRecipeBuilderJS`](../API/KubeJS#machinerecipebuilderjs) 同样提供 `requiredHost(String)` / `requiredHosts(String...)` 方法。

### 数据组件匹配

```js
item: 'minecraft:potion',
components: {
    'minecraft:potion_contents': {
        potion: 'minecraft:water'
    }
}
```

输入物品字段下加 `components`，MMCR 会按 [DataComponentPredicateSet](../API/JavaAPI#datacomponentpredicateset) 规则精确匹配数据组件。

输出物品的 `stack` 下也可以加 `components`，作为输出物品的组件值。这个机制让 KubeJS 端能完整支持药水、附魔书等带组件物品。

## 特殊机制：HOST + MODULE

### 什么是 host，什么是 module

- **host（主机）**：通过 `.host(String...)` 声明自己接受哪些模块机器的"大机器"。  
    主机决定哪些模块可以连接；它自身的成型与配方不要求模块存在。  
- **module（模块）**：通过 `.module()` 标记自己是模块机器。  
    模块结构匹配与主机连接是不同状态；独立成型不代表可运行，运行需有效主机连接。  

本文的 HOST 通过 `.host("mmcr_kubejs:kubejs_space_reassembler")` 接受重组机。重组机通过 `.module()` 声明自己是模块。两边的 ID 必须严格匹配，`host(...)` 接受的是模块的注册 ID，模块的注册 ID 由 `createMachine(...)` 给出。

### `expandableStructure` 与耦合器的关系

KubeJS 端有 [`MachineBuilderJS.expandableStructure()`](../API/KubeJS#machinebuilderjs)，启用后允许结构进入"扩展形态"。

本教程的电梯与重组机没有显式调用 `.expandableStructure()`，因为它们是**两台独立的多方块结构**通过 `coupler()` 拼合，而不是单台机器的"主结构 + 扩展结构"两阶段。

如果你想表达"一台机器的扩展结构"，例如炼油塔的蒸馏塔架，再考虑 `.expandableStructure()`。

如果你想表达"两台机器共享世界空间"，也就是 HOST/MODULE，使用 `.host(...)` + `.module()` + `api.coupler()`。

### 配方的 `required_host_ids`

重组机本来就要求连接主机，配方名单再限定主机种类：

- 没有 `required_host_ids`：任意有效连接且接受该模块的主机都可满足连接门槛。
- 有 `required_host_ids`：当前连接主机还须在名单内；连接失效后运行门槛不再满足，配方暂停 / 失败行为由运行时与失败策略处理，不承诺“拆除的同一瞬间”停止。

太空电梯 选择了后者，意义在于"必须在电梯上进行"。

### 配方池、并行与大数能耗

重组机定义了 5 个有序池，本例配方实际用了 `kubejs_space_reassembler` 和 `kubejs_space_miner`；`space_1/2/3` 暂无示例配方。多池会扩大实际配方检索范围，不只是 JEI 分类。每份 JSON 仍只有一个 `recipe_pool`。

第四条配方的 `MMCR.getValues().INT_MAX * 2` 等于 `4294967294`，能量 codec 使用 `long`，不是按 `int` 截断。它仍需实际端口传输与供电能力。机器没有开启 `allowParallelism()`，所以前三条 JSON 虽写了 `parallelized: true`，也不会单独开启机器并行。重组机的 `allowMultithreading()` 与结构中的 `factory_controller` 配合允许工厂调度，定义侧线程上限默认 1，可通过 `factoryThreads(int)` 配置；JSON `max_threads` 未写时也默认 1。
