# A_Module_Machine — 宿主 + 模块（太空电梯 + 太空重组机）

本文演示 MMCR 的 **HOST + MODULE** 模式：一台"宿主"大机器旁边挂一台"模块"小机器，模块的配方只在宿主在场时才会跑。代码对应 [Java 端的 SPACE](../JavaAPI/太空电梯)，两边的命名差异很小。

## 机器简介

`A_Module_Machine` 由两个示例文件组成——一台电梯、一台重组机：

- `example/startup_scripts/A_Module_Machine.js` — 注册 `kubejs_space_elevator`（HOST）和 `kubejs_space_reassembler`（MODULE）两台机器。
- `example/server_scripts/structure/A_Module_Machine.js` — 电梯结构是一根 17 层高的石英塔；重组机结构是一个 3×4×3 的小盒子。
- `example/server_scripts/recipe/A_Module_Machine.js` — 电梯配方（苹果 → 金苹果）和重组机配方（水药 → 治疗药水，附带 `required_host_ids` 限定）。

HOST 与 MODULE 之间的关系有三层：

1. **机器层**：宿主通过 `.host(...)` 声明自己接受哪些模块；模块通过 `.module()` 标记自己可被宿主接纳。
2. **结构层**：两台机器的 `.pattern` 各放一个 `api.coupler()` 方块谓词；这两个耦合器必须在世界相邻或重合时两台才算同时成型。
3. **配方层**：模块的配方 `required_host_ids` 列出宿主 ID——只有宿主在场时该配方才能被选中。

这三层约束缺一不可：哪怕两台机器都成型了，没有 `required_host_ids` 的模块配方也会被允许独立运行。

## 机器定义详解（`MMCREvents.startup`）

打开 `startup_scripts/` 目录下的 [A_Module_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/startup_scripts/A_Module_Machine.js)：

```js
// Register a host machine and a module machine.
// This example is based on GTL's space elevator.

MMCREvents.startup(event => {
    const space_elevator = event
        .createMachine("mmcr_kubejs:kubejs_space_elevator")
        .displayNameKey("machine.mmcr_kubejs.kubejs_space_elevator")
        .recipeFamily("mmcr_kubejs:kubejs_space_elevator")
        .appearance('minecraft:smooth_quartz')
        .controllerBaseTexture('minecraft:block/quartz_block_bottom') // Smooth quartz has no standard texture, so set the base texture manually.
        .formedPortBaseTexture('minecraft:block/quartz_block_bottom')
        .host("mmcr_kubejs:kubejs_space_reassembler")

    const space_reassembler = event
        .createMachine("mmcr_kubejs:kubejs_space_reassembler")
        .displayNameKey("machine.mmcr_kubejs.kubejs_space_reassembler")
        .recipeFamily("mmcr_kubejs:kubejs_space_reassembler")
        .appearance('minecraft:quartz_pillar')
        .module()


    space_elevator.register()
    space_reassembler.register()
})
```

这个脚本里有两台机器在同一个 `MMCREvents.startup` 回调里注册。注意 KubeJS 没有显式的 `MachineRole` 枚举，角色通过 `.host(...)` 和 `.module()` 这两个链式方法表达。

### 电梯（HOST）

```js
const space_elevator = event
    .createMachine("mmcr_kubejs:kubejs_space_elevator")
    .displayNameKey("machine.mmcr_kubejs.kubejs_space_elevator")
    .recipeFamily("mmcr_kubejs:kubejs_space_elevator")
    .appearance('minecraft:smooth_quartz')
    .controllerBaseTexture('minecraft:block/quartz_block_bottom')
    .formedPortBaseTexture('minecraft:block/quartz_block_bottom')
    .host("mmcr_kubejs:kubejs_space_reassembler")
```

- `.displayNameKey(...)`：本地化键，遵循 `machine.<命名空间>.<注册名>` 约定。
- `.recipeFamily(...)`：把电梯和它的配方绑定到同一族；详见 [API/KubeJS#recipefamilystring-recipefamilyid--machinebuilderjs](../API/KubeJS#machinebuilderjs)。
- `.appearance('minecraft:smooth_quartz')`：控制器的默认外观方块。
- `.controllerBaseTexture(...)` / `.formedPortBaseTexture(...)`：smooth_quartz 没有标准的方块纹理，需要手动指定 base 纹理。这两个方法对应 Java 端 `AppearanceSpec.controllerBaseTexture` / `formedPortBaseTexture`。
- **`.host("mmcr_kubejs:kubejs_space_reassembler")`**：声明这台电梯接受 `kubejs_space_reassembler` 作为模块机器。参数是变长 `String...`，可以一次声明多个模块。详见 [API/KubeJS#machinebuilderjs](../API/KubeJS#machinebuilderjs)。

### 重组机（MODULE）

```js
const space_reassembler = event
    .createMachine("mmcr_kubejs:kubejs_space_reassembler")
    .displayNameKey("machine.mmcr_kubejs.kubejs_space_reassembler")
    .recipeFamily("mmcr_kubejs:kubejs_space_reassembler")
    .appearance('minecraft:quartz_pillar')
    .module()
```

`.module()` 是无参版本，等价于 `.module(true)`，把模块开关置为 `true`。这是模块机器的**唯一必备调用**——只要 `.module()` 一旦被调用，`MachineBuilderJS` 就拒绝再把它当 `NORMAL` 注册，并在 `register()` 阶段校验：要么显式声明 `host(...)`，要么作为模块存在。

`.host(...)` 和 `.module()` 在 [API/KubeJS#machinerole-string--machinebuilderjs](../API/KubeJS#role-string--machinebuilderjs) 的 API 参考里被标注为与显式 `role("HOST")` / `role("MODULE")` 等价的两条捷径；KubeJS 端没有暴露字符串角色参数，但行为一致。

> 备注：KubeJS 端没有等价的 `.acceptedModule(...)` 命名；`.host(...)` 在内部就是 `acceptedModule(...)` 的别名。详见 [API/KubeJS#machinebuilderjs](../API/KubeJS#machinebuilderjs)。

### 启动期不可热加载

和 A_Simple_Machine 一样，机器定义必须重启游戏才能生效，详见 [API/KubeJS#mmcrstartupeventjs](../API/KubeJS#mmcrstartupeventjs) 的"注意事项"小节。

## 结构详解（`MMCREvents.server`）

打开 `server_scripts/structure/` 目录下的 [A_Module_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/server_scripts/structure/A_Module_Machine.js)：

```js
MMCREvents.server(event => {
    const api = event.getAPI()

    const space_elevator = event.createStructure("mmcr_kubejs:kubejs_space_elevator")

    space_elevator
        .pattern(['        X        ','                 ','                 ', /* ...省略多层... */])
        // ... 共 17 层 .pattern 调用
        .set('X' ,api.block('minecraft:smooth_quartz'))
        .set('A' ,api.block('minecraft:amethyst_block'))
        .set('B' ,api.coupler())                 // ← 电梯端的 coupler 槽位
        .set('D' ,api.anyOf(
            api.block('minecraft:smooth_quartz'),
            api.anyOfItemInput(),
            api.anyOfItemOutput(),
            api.anyOfEnergyInput()
        ))
        .controller('E')
        .build()

    const space_reassembler = event.createStructure("mmcr_kubejs:kubejs_space_reassembler")

    space_reassembler
        .pattern(['AAA','XBX','XBX','XDX'])
        .pattern(['AAA','BEB','B B','DDD'])
        .pattern(['AAA','XFX','XBX','XDX'])
        .set('X',api.block('minecraft:quartz_pillar'))
        .set('A',api.block('minecraft:amethyst_block'))
        .set('B',api.anyOf(
            api.block('minecraft:smooth_quartz'),
            api.anyOfItemInput(),
            api.anyOfItemOutput(),
            api.anyOfEnergyInput()
        ))
        .set('D', api.block('minecraft:glass'))
        .set('E',api.coupler())                  // ← 重组机端的 coupler 槽位
        .controller('F')
        .build()
})
```

### 耦合器是 HOST/MODULE 的物理拼合点

电梯结构里有三个 `B` 字符，每个 `B` 都绑定到 `api.coupler()`：

```js
.set('B' ,api.coupler())
```

重组机结构里有一个 `E` 字符，也绑定到 `api.coupler()`：

```js
.set('E',api.coupler())
```

`api.coupler()` 返回 [`BlockPredicate`](../API/KubeJS#coupler--blockpredicate)，专门用来表示"机器耦合器"方块——MMCR 在成型判定时会把**两台机器的耦合器位置重合**视为两台同时成型。电梯的耦合器可以摆多个（每个 `B` 都是候选位置），重组机的耦合器只有一个（`E`）。

### 端口与控制器

电梯结构和 A_Simple_Machine 类似，`D` 槽位是物品输入 / 输出 / 能量输入的并集，方便在塔身任意方向接端口。控制器在 `E`，位于塔顶。重组机的 `B` 槽位同样是端口并集，但用空格 `' '` 在内部挖空（参考 A_Simple_Machine 的处理方式）。

### 结构在生产构建中不可热加载

参见 [API/KubeJS#machinestructurebuilderjs](../API/KubeJS#machinestructurebuilderjs) 的 `build()` 注意事项。

## 配方详解（`ServerEvents.recipes`）

打开 `server_scripts/recipe/` 目录下的 [A_Module_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/main/example/server_scripts/recipe/A_Module_Machine.js)：

```js
ServerEvents.recipes(event => {
    // 重组机配方：带 required_host_ids
    event.custom({
        type: 'mmcr:machine_recipe',
        machine: 'mmcr_kubejs:kubejs_space_reassembler',
        tick_time: 100,
        parallelized: true,
        required_host_ids: [
            "mmcr_kubejs:kubejs_space_elevator"
        ],                                          // ← 只有宿主在场时才跑
        requirements: [
            {
                type: 'minecraft:item',
                io: 'input',
                item: 'minecraft:potion',
                components: {
                    'minecraft:potion_contents': {
                        potion: 'minecraft:water'
                    }
                },
                count: 1
            },
            {
                type: 'minecraft:item',
                io: 'output',
                stack: {
                    id: 'minecraft:potion',
                    count: 1,
                    components: {
                        'minecraft:potion_contents': {
                            potion: 'minecraft:healing'
                        }
                    }
                }
            },
            {
                type: 'neoforge:energy',
                io: 'input',
                fe_per_tick: 100
            }
        ]
    })

    // 电梯配方：普通配方，宿主本身也能跑
    event.custom({
        type: 'mmcr:machine_recipe',
        machine: 'mmcr_kubejs:kubejs_space_elevator',
        tick_time: 1000,
        parallelized: true,
        requirements: [
            { type: 'minecraft:item', io: 'input',  item: 'minecraft:apple', count: 1 },
            { type: 'minecraft:item', io: 'output', stack: { id: 'minecraft:golden_apple', count: 12 } },
            { type: 'neoforge:energy', io: 'input',  fe_per_tick: 100 }
        ]
    })
})
```

### 数据驱动配方的 `required_host_ids` 字段

```js
required_host_ids: [
    "mmcr_kubejs:kubejs_space_elevator"
]
```

这是数据驱动配方的顶层字段，对应 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema) 上的 `required_host_ids` 键；语义是把当前配方的"宿主限定"列出来。MMCR 在选取配方时会把"宿主是否成型"作为附加校验：只要列表中的任意一个宿主在当前 tick 内是成型状态，配方便可被选中。

字段值为 `String` 数组，数组中的 ID 对应宿主机器的注册 ID（与启动期 `.createMachine(...)` 的字符串一致）。若该字段缺失或为空数组，配方视为无宿主限定，模块机器即使在没有宿主的情况下也能跑。

> 与 Java 端 `MachineRecipeBuilder.requiredHost(...)` 等价。KubeJS 数据驱动配方直接使用顶层字段；编程式 [`MachineRecipeBuilderJS`](../API/KubeJS#machinerecipebuilderjs) 同样提供 `requiredHost(String)` / `requiredHosts(String...)` 方法。

### 数据组件匹配

```js
item: 'minecraft:potion',
components: {
    'minecraft:potion_contents': {
        potion: 'minecraft:water'
    }
}
```

输入物品字段下加 `components`，MMCR 会按 [DataComponentPredicateSet](../API/JavaAPI#datacomponentpredicateset) 规则精确匹配数据组件。输出物品的 `stack` 下也可以加 `components`，作为输出物品的组件值。这个机制让 KubeJS 端能完整支持药水、附魔书等带组件物品。

## 特殊机制：HOST + MODULE

### 什么是 host，什么是 module

- **host（宿主）**：通过 `.host(String...)` 声明自己接受哪些模块机器的"大机器"。宿主决定哪些模块能挂在自己身上，没有被任何宿主 `.host(...)` 接受的模块机器在世界里无法成型（即便单独摆出模块结构也不行）。
- **module（模块）**：通过 `.module()` 标记自己是模块机器。模块机器需要被至少一台宿主 `.host(...)` 才能工作。

电梯这台 HOST 通过 `.host("mmcr_kubejs:kubejs_space_reassembler")` 接受重组机；重组机通过 `.module()` 声明自己是模块。两边的 ID 必须严格匹配——`host(...)` 接受的是模块的注册 ID，模块的注册 ID 由 `createMachine(...)` 给出。

### `expandableStructure` 与耦合器的关系

KubeJS 端有 [`MachineBuilderJS.expandableStructure()`](../API/KubeJS#machinebuilderjs)，启用后允许结构进入"扩展形态"。本教程的电梯与重组机没有显式调用 `.expandableStructure()`，因为它们是**两台独立的多方块结构**通过 `coupler()` 拼合，而不是单台机器的"主结构 + 扩展结构"两阶段。

如果你想表达"一台机器的扩展结构"——比如炼油塔的蒸馏塔架——再考虑 `.expandableStructure()`；如果你想表达"两台机器共享世界空间"——也就是 HOST/MODULE——就靠 `.host(...)` + `.module()` + `api.coupler()`。

### 配方的 `required_host_ids` 决定"什么时候跑"

光有结构上的耦合器还不够，重组机的配方必须额外声明 `required_host_ids` 才能让自己"只在宿主旁边跑"。这是设计上的取舍：

- 没有 `required_host_ids`：模块配方能独立运行，宿主就只是一个"装饰品"。
- 有 `required_host_ids`：模块配方受宿主成型状态约束，宿主毁了或拆了，模块配方立刻停下。

A_Module_Machine 选择了后者——药水转化的仪式性意义就在于"必须在电梯旁边进行"。

## 与其他教程的对比

### 与 A_Simple_Machine 的对比

| 维度 | A_Simple_Machine | A_Module_Machine |
| --- | --- | --- |
| 机器数量 | 1 台 | 2 台（HOST + MODULE） |
| 启动期独有调用 | 无 | `.host(...)` / `.module()` |
| 结构层独有谓词 | 普通方块谓词 | `api.coupler()` |
| 配方层独有字段 | 无 | `required_host_ids` |

A_Simple_Machine 是 KubeJS 端的"最小可运行机器"，A_Module_Machine 在此基础上加了"两台机器如何互联"。

### 与 Java 端 SPACE 的对比

A_Module_Machine 与 [SPACE](../JavaAPI/太空电梯) 是同一对电梯 + 重组机在 KubeJS 与 Java 端的两个实现。关键差异：

| Java 端 | KubeJS 端 |
| --- | --- |
| `MachineRole.HOST` + `MachineBuilder.acceptedModule(...)` | `MachineBuilderJS.host(...)` |
| `MachineRole.MODULE` | `MachineBuilderJS.module()` |
| `MachineStructureBuilder.coupler()` | `KubeJSApi.coupler()` |
| `MachineRecipeBuilder.requiredHost(...)` | 数据驱动 `required_host_ids` 字段 |

Java 端使用 `MachineRole` 枚举显式表达角色；KubeJS 端通过 `.host(...)` / `.module()` 这两个开关隐式设定角色。`requiredHost(...)` 在 Java 端是逐条添加，在 KubeJS 数据驱动配方里是顶层数组字段——后者更接近 JSON 数据驱动的自然写法。
