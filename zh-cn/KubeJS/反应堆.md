# 反应堆 - 带方块状态的机器

本文演示一台用方块状态（Block State）精确描述结构的机器。代码对应三个文件：

- `example/startup_scripts/A_BlockState_Machine.js`
- `example/server_scripts/structure/A_BlockState_Machine.js`
- `example/server_scripts/recipe/A_BlockState_Machine.js`

这是 KubeJS 示例里**第一次**出现 `api.state(...)` 谓词和方块精确朝向的形态。

## 概览

反应堆 与 [高炉](高炉) 的关键差异在于**结构匹配粒度**：

- 高炉 用 `api.block(...)` 描述外壳，即任意状态都算匹配。
- 反应堆 用 `api.state(...)` 精确指定方块的**全部属性值**，即 `facing`、`shape`、`waterlogged` 等一一对齐。

反应堆结构有染色玻璃、绿宝石块、青金石块、楼梯和能量输出端口。楼梯多用 `api.state(...)`，无须限定属性的玻璃、外壳等仍用 `api.block(...)`。两类谓词可以混合使用。

## 机器定义

`startup_scripts`目录下的 [A_BlockState_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/startup_scripts/A_BlockState_Machine.js)：

```js
// Define a more complex machine that uses block states.
MMCREvents.startup(event => {

    const builder = event
        .createMachine("mmcr_kubejs:kubejs_reactor") // Create the machine definition.
        .displayNameKey("machine.mmcr_kubejs.kubejs_reactor") // Translation key for the display name.
        .recipePool("mmcr_kubejs:kubejs_reactor") // Bind the recipe pool.
        .appearance("minecraft:blue_ice") // Set the controller's appearance block.

    builder.register()
    // See server_scripts/structure/A_BlockState_Machine.js for the block-state structure.
})
```

`MMCREvents.startup(event => {...})` 把事件对象传入回调。
`event` 是 [MMCRStartupEventJS](../API/KubeJS#mmcrstartupeventjs)。
`event.createMachine(...)` 返回 [MachineBuilderJS](../API/KubeJS#machinebuilderjs)。

链式调用：

- `.createMachine()`：注册 ID。
- `.displayNameKey()`：本地化键。详见 [MachineBuilderJS.displayNameKey](../API/KubeJS#machinebuilderjs)。
- `.recipePool()`：配方池 ID。

    这是**实际配方检索用的池 ID**，配方 JSON 的 `recipe_pool` 必须属于机器声明的池。机器 ID 与池 ID 可以不同，一个机器可以声明多个池，一份配方只选一个池。详见 [MachineBuilderJS.recipePool](../API/KubeJS#recipepool-string-recipepoolids-%E2%86%92-machinebuilderjs)。

    `recipePool` 是机器定义层用于配方分组与广播的标识，决定机器配方如何被注册、检索与同步到 JEI 与重载流水线。
- `.appearance()`：把控制器的外观方块设为蓝冰。详见 [MachineBuilderJS.appearance](../API/KubeJS#machinebuilderjs)。这一步同时会自动派生出控制器底纹理与成型端口底纹理。

`builder.register()` 终结，把机器提交到启动期注册窗口。

:::info 备注
这台机器没有 `.allowMultithreading()`、`.allowParallelism()`、`.maxParallelAmount(...)`。MMCR 默认多线程与并行都是关闭的，反应堆不需要并行控制器。
:::

启动期窗口不可热加载。修改后必须重启游戏。

## 多方块结构

`server_scripts/structure/` 目录下的 [A_BlockState_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/server_scripts/structure/A_BlockState_Machine.js)，下列补全结构并显式开启状态敏感：

```js
MMCREvents.server(event => {
    const api = event.getAPI()
    const structure = event.createStructure("mmcr_kubejs:kubejs_reactor")

    structure
        .stateSensitive()
        .pattern("  ABBBD  ", "         ", "         ", "         ", "         ", "         ", "         ", "         ")
        .pattern(" AEXXXFD ", "   XXX   ", "         ", "         ", "         ", "         ", "         ", "         ")
        .pattern("AEXXXXXFD", "  GHHHG  ", "  GHHHG  ", "  GHHHG  ", "  IJJJK  ", "         ", "         ", "         ")
        .pattern("LXXXXXXXM", " XHNONHX ", "  HNONH  ", "  HNONH  ", "  PXXXQ  ", "   RRR   ", "         ", "         ")
        .pattern("LXXXXXXXM", " XHOXOHX ", "  HOXOH  ", "  HOXOH  ", "  PXXXQ  ", "   RSR   ", "    S    ", "    T    ")
        .pattern("LXXXXXXXM", " XHNONHX ", "  HNONH  ", "  HNONH  ", "  PXXXQ  ", "   RRR   ", "         ", "         ")
        .pattern("UVXXXXXWY", "  GHHHG  ", "  GHHHG  ", "  GHHHG  ", "  Zaaab  ", "         ", "         ", "         ")
        .pattern(" UVXXXWY ", "   XCX   ", "         ", "         ", "         ", "         ", "         ", "         ")
        .pattern("  UcccY  ", "         ", "         ", "         ", "         ", "         ", "         ", "         ")
        .set('X', api.anyOf(
            api.anyOfItemInput(),
            api.anyOfItemOutput(),
            api.anyOfFluidOutput(),
            api.anyOfFluidInput(),
            api.anyOfEnergyOutput(), // This reactor can output energy without requiring an energy input port.
            api.block('minecraft:blue_ice')
        ))
        .set('A', api.state('minecraft:deepslate_brick_stairs[facing=east,half=bottom,shape=outer_right,waterlogged=false]'))
        .set('B', api.state('minecraft:deepslate_brick_stairs[facing=south,half=bottom,shape=straight,waterlogged=false]'))
        .set('D', api.state('minecraft:deepslate_brick_stairs[facing=south,half=bottom,shape=outer_right,waterlogged=false]'))
        .set('E', api.state('minecraft:deepslate_brick_stairs[facing=south,half=bottom,shape=inner_left,waterlogged=false]'))
        .set('F', api.state('minecraft:deepslate_brick_stairs[facing=west,half=bottom,shape=inner_left,waterlogged=false]'))
        .set('G', api.block('minecraft:polished_deepslate'))
        .set('H', api.block('minecraft:black_stained_glass'))
        .set('I', api.state('minecraft:polished_deepslate_stairs[facing=east,half=bottom,shape=outer_right,waterlogged=false]'))
        .set('J', api.state('minecraft:polished_deepslate_stairs[facing=south,half=bottom,shape=straight,waterlogged=false]'))
        .set('K', api.state('minecraft:polished_deepslate_stairs[facing=west,half=bottom,shape=outer_left,waterlogged=false]'))
        .set('L', api.state('minecraft:deepslate_brick_stairs[facing=east,half=bottom,shape=straight,waterlogged=false]'))
        .set('M', api.state('minecraft:deepslate_brick_stairs[facing=west,half=bottom,shape=straight,waterlogged=false]'))
        .set('N', api.block('minecraft:emerald_block'))
        .set('O', api.block('minecraft:lapis_block'))
        .set('P', api.state('minecraft:polished_deepslate_stairs[facing=east,half=bottom,shape=straight,waterlogged=false]'))
        .set('Q', api.state('minecraft:polished_deepslate_stairs[facing=west,half=bottom,shape=straight,waterlogged=false]'))
        .set('R', api.block('minecraft:deepslate_brick_slab'))
        .set('S', api.block('minecraft:deepslate_tiles'))
        .set('T', api.block('minecraft:oxidized_lightning_rod'))
        .set('U', api.state('minecraft:deepslate_brick_stairs[facing=east,half=bottom,shape=outer_left,waterlogged=false]'))
        .set('V', api.state('minecraft:deepslate_brick_stairs[facing=north,half=bottom,shape=inner_right,waterlogged=false]'))
        .set('W', api.state('minecraft:deepslate_brick_stairs[facing=north,half=bottom,shape=inner_left,waterlogged=false]'))
        .set('Y', api.state('minecraft:deepslate_brick_stairs[facing=west,half=bottom,shape=outer_right,waterlogged=false]'))
        .set('Z', api.state('minecraft:polished_deepslate_stairs[facing=east,half=bottom,shape=outer_left,waterlogged=false]'))
        .set('a', api.block('minecraft:polished_deepslate_stairs'))
        .set('b', api.state('minecraft:polished_deepslate_stairs[facing=north,half=bottom,shape=outer_left,waterlogged=false]'))
        .set('c', api.state('minecraft:deepslate_brick_stairs[facing=north,half=bottom,shape=straight,waterlogged=false]'))
        .controller('C')
        .build()
})
```

`MMCREvents.server(event => {...})` 回调里的 `event` 是 [MMCRServerEventJS](../API/KubeJS#mmcrservereventjs)。
`event.getAPI()` 返回 [KubeJSApi](../API/KubeJS#kubejsapi)，下文统一用 `api` 指代。
`event.createStructure(...)` 返回 [MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs)。

与 [高炉](高炉) 相比，本机器的结构有两个**关键差异**：

1. 官方脚本未调用 `stateSensitive()`，默认状态不敏感。本文补上该调用后，`api.state(...)` 的属性才会参与实际成型匹配；`api.block(...)` 仍只匹配方块，不会被升级为默认状态匹配。
2. `X` 字符的并集较宽，包含 5 种端口和蓝冰：`anyOfItemInput`、`anyOfItemOutput`、`anyOfFluidOutput`、`anyOfFluidInput`、`anyOfEnergyOutput`、再加 `minecraft:blue_ice`。这是因为反应堆同一外壳方块位既允许端口，也允许作为装饰的蓝冰。

`.controller('C')` 把 C 字符（按 1 起算位于第 8 z 层、第 2 y 行）标记为控制器位置。`.build()` 返回 `void`，向当前服务脚本重载事务提交结构。

:::info 备注

导出工具给出的是声明起点，不保证每个有方向方块都导出为状态谓词。官方脚本的 `a` 使用 `api.block('minecraft:polished_deepslate_stairs')`，这里仍允许任意楼梯状态；需要限定朝向时应按实际搭建结果改为 `api.state(...)`。标准方向属性可以随结构旋转处理，但非标准模组属性及无法由 Minecraft 表示的竖直楼梯不能假设自动支持。
:::

## 配方

`server_scripts/recipe/` 目录下的 [A_BlockState_Machine.js](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/server_scripts/recipe/A_BlockState_Machine.js)：

```js
ServerEvents.recipes(event => {
    event.custom({
        type: 'mmcr:machine_recipe',
        recipe_pool: 'mmcr_kubejs:kubejs_reactor',
        tick_time: 300,
        requirements: [
            { type: 'minecraft:item', io: 'input', item: 'minecraft:apple', count: 3 },
            { type: 'minecraft:fluid', io: 'input', fluid: 'minecraft:water', amount: 1 },
            { type: 'minecraft:item', io: 'output', stack: { id: 'minecraft:diamond', count: 10 } },
            { type: 'minecraft:fluid', io: 'output', stack: { id: 'minecraft:lava', amount: 250 } },
            { type: 'neoforge:energy', io: 'output', fe_per_tick: 200 }
        ]
    })

    // This recipe cannot run because the structure has no energy input port.
    // The requirement and recipe systems are intentionally independent.
    event.custom({
        type: 'mmcr:machine_recipe',
        recipe_pool: 'mmcr_kubejs:kubejs_reactor',
        tick_time: 200,
        requirements: [
            { type: 'minecraft:item', io: 'input', item: 'minecraft:golden_apple', count: 2 },
            { type: 'minecraft:fluid', io: 'input', fluid: 'minecraft:water', amount: 800 },
            { type: 'minecraft:item', io: 'output', stack: { id: 'minecraft:gold_ingot', count: 2 } },
            { type: 'minecraft:fluid', io: 'output', stack: { id: 'minecraft:lava', amount: 450 } },
            { type: 'neoforge:energy', io: 'input', fe_per_tick: 10 },
            { type: 'neoforge:energy', io: 'output', fe_per_tick: 200 }
        ]
    })
})
```

两份配方展示了 `requirements` 系统与 `recipe` 系统的**有意分离**：

- 第一份只声明 `neoforge:energy` 的 **output** 方向，符合反应堆"对外输出能量"的设定。
- 第二份同时声明了 energy 的 **input** 与 output。但是结构里**没有任何能量输入端口**，这条配方在结构成型后仍能被加载、却**永远无法运行**（没有匹配的输入端口）。

字段含义详见 [MachineRecipeSchema](../API/KubeJS#machinerecipeschema)。

数据驱动的配方支持热加载，修改后 `/reload` 即可。

## 特殊机制：`api.state(...)` 与 `api.block(...)` 的区别

这是 反应堆 与前面所有示例最大的不同点。

### `api.block(...)`：方块任意状态都算匹配

参见 [KubeJSApi.block](../API/KubeJS#kubejsapi)：

```javascript
const casing = api.block("minecraft:iron_block")
```

返回的 `BlockPredicate` 只比对**方块 ID**，无论方块是什么属性值都算匹配。

上述示例是来自 高炉 的写法。玩家在 4 个角位既可以放铁块任意形态(虽然实际上只有一种形态)，都不影响结构成型。

### `api.state(...)`：方块状态必须精确匹配

参见 [KubeJSApi.state](../API/KubeJS#kubejsapi)：

```javascript
const log = api.state("minecraft:oak_log[axis=x]")
```

`api.state(String)` 从方块默认状态出发，再覆盖括号内的属性，因此省略的属性不是通配符，而是保留默认值。返回的 `OfBlockState` 谓词本身能精确比对所有属性；结构实际匹配是否使用这些属性，由 `stateSensitive` 决定。属性名未知、属性值无效或方块 ID 不存在都会被拒绝。

反应堆用 `api.state(...)` 限定带朝向与形状属性的楼梯；这里的黑色染色玻璃是完整玻璃方块，仍由 `api.block(...)` 匹配。

这些方块默认放置会有不同的 `facing`/`shape`/`waterlogged` 属性。要想让结构拼合正确，模式里每个字符都必须写出确切的状态值，例如：

```javascript
.set('A', api.state('minecraft:deepslate_brick_stairs[facing=east,half=bottom,shape=outer_right,waterlogged=false]'))
```

这行说的是："A 位置必须是一块朝东、底层、`outer_right` 形状、未浸水的深板岩砖楼梯。" 玩家摆放时也要用相同状态的楼梯，**任何其他状态都会导致结构失配**。

### `stateSensitive()` / `stateInsensitive()`

[MachineStructureBuilderJS](../API/KubeJS#machinestructurebuilderjs) 的两个顶层方法：

| 方法 | 行为 |
| --- | --- |
| [`stateSensitive()`](../API/KubeJS#machinestructurebuilderjs) | 使用谓词原有匹配规则：`api.state(...)` 精确匹配状态，`api.block(...)` 仍只匹配方块。 |
| [`stateInsensitive()`](../API/KubeJS#machinestructurebuilderjs) | 把整个结构设为状态不敏感，所有用 `api.state(...)` 绑定的字符降级为只比对方块 ID。 |

`MachineStructureBuilderJS` 默认 `stateSensitive = false`。仅写 `api.state(...)` 不足以开启全局状态匹配，因此本文在外层结构链上增加 `.stateSensitive()`；分组结构也应在外层设置，不是在 stage 回调里调用。

混合写法本身合法。开状态敏感后，楼梯按显式状态检查、外壳按方块检查；改用 `stateInsensitive()` 时，状态谓词降级为方块检查。空格表示不检查该位置，要求确实为空气时应绑定 `api.air()`。

## 小结

1. 用 `api.state(...)` 加外层 `stateSensitive()` 精确控制楼梯等方块的状态；不需要限定状态的方块保留 `api.block(...)`。
2. `api.anyOf(BlockPredicate...)` 把多种端口与外壳并集：`X` 允许 5 种端口和蓝冰，其中有能量输出、没有能量输入。
3. 配方系统与端口系统有意解耦：配方可以声明任何方向的 energy 需求，运行时不匹配端口也不会让配方加载失败，但执行时会失败。
