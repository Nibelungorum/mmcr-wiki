# 数据存储测试机器 — KubeJS 数据存储机器

本文是 KubeJS 进阶示例的第一篇。

回调使用 `api.machine.definition.TickBehaviorContext` 与底层 `MachineIoPlan`，不是 Java `publicapi`。本提交的官方脚本仍用 `commit(transaction => storage.set(..., api.dataValue(next), transaction))`，但当前存储视图要求包装后的事务类型，而且它的 `Object` 重载不接受底层 `api.data.DataValue`；下文将这两处改为 `commitData(transaction => storage.set(..., next, transaction))`，直接传入 `BigInteger`，其余数据流保留。
## 机器

数据存储测试机器 是一台**没有配方**的能量存储方块，中心嵌一颗数据存储接口方块：

1. 每 5 tick 用**二分查找**探测当前能从能量输入端口提取的最大 FE，提交成功后写入 `BigInteger` 计数
2. 每 5 tick 再退库：把存储的 FE 写入能量输出端口，端口向外部设备供电是后续独立过程
3. 储量保存在关联数据存储方块的 `DataStorage` 中，随方块实体存档；不承诺异常退出或拆除方块后仍保留
4. tick 回调写出当前储量的控制器屏幕文本

## 机器定义详解

启动期脚本 [`A_Data_Storage_Machine.js`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/example/startup_scripts/advance/A_Data_Storage_Machine.js)：

```javascript
MMCREvents.startup(event => {
    const machine = event
        .createMachine("mmcr_kubejs:kubejs_data_storage_machine")
        .displayNameKey("machine.mmcr_kubejs.kubejs_data_storage_machine")
        .recipePool("mmcr_kubejs:kubejs_data_storage_machine")
        .appearance("minecraft:crying_obsidian");
    // ... 见下文
    machine.register()
})
```

链式调用 4 个方法：

- `.displayNameKey(...)`：声明本地化键。
- `.recipePool(...)`：把机器绑到一个配方池 ID。本机器**没有配方**，但仍设置配方池 ID。
- `.appearance("minecraft:crying_obsidian")`：外观方块为哭泣的黑曜石。
- `.tickBehavior(...)`：把行为切到直 tick 模式，**此时不可以**调用 `.recipeBehavior(...)`，这两者在 [`MachineBuilderJS`](../API/KubeJS#machinebuilderjs) 里互斥。

声明几个会反复用到的常量：

```javascript
const BigInteger = Java.loadClass("java.math.BigInteger")
const api = MMCR.getAPI()
const RecipeIO = api.recipeIO()
const OutputPolicy = api.outputPolicy()
const INT_MAX = MMCR.getValues().INT_MAX
```

逐个解释：

- `Java.loadClass("java.math.BigInteger")`：虚拟储量使用任意精度整数。MMCR 底层能量存储和需求使用 `long`；示例主动把每轮请求限制为 `INT_MAX`，不能据此断言所有端口只有 `int` 容量。
- `MMCR.getAPI()` 返回 [`KubeJSApi`](../API/KubeJS#kubejsapi)，下文统一用 `api` 指代。渲染储量字符串走 [`api.readableNumberBigInt(...)`](../API/KubeJS#readablenumberbigintbiginteger-value--string)。
- `api.recipeIO()` 返回 [`RecipeIoValues`](../API/KubeJS#recipeio--recipeiovalues) 常量对象，本教程里用到 `.INPUT` / `.OUTPUT` 两个方向枚举。
- `api.outputPolicy()` 返回 [`OutputPolicyValues`](../API/KubeJS#outputpolicy--outputpolicyvalues) 常量对象。本教程用到 `.ALLOW_PARTIAL`，即允许部分接受。
- `MMCR.getValues()` 返回 [`MMCRValues`](../API/KubeJS#getvalues--mmcrvalues)，`.INT_MAX` 是 `Integer.MAX_VALUE`，此处用于限制单轮搬运量。

## 数据流详解（tick 行为）

核心逻辑在 `.tickBehavior(behavior => behavior.serverTick(ctx => { ... }))` 的回调里。

### 1. 读取当前储量

```javascript
const api = MMCR.getAPI()       // 已经在外面取过；这里仅为引用
const RecipeIO = api.recipeIO()
const OutputPolicy = api.outputPolicy()
const INT_MAX = MMCR.getValues().INT_MAX

machine.tickBehavior(behavior => behavior
    .serverTick(ctx => {
        var storage = ctx.dataStorage()
        if (storage == null) return

        // get big integer data from data storage
        var stored = BigInteger.ZERO
        var saved = storage.get("energy")

        if (saved.isPresent()) {
            stored = saved.get()
                .asBigInteger()
                .orElse(BigInteger.ZERO)
        }
        // ...
    })
)
```

`ctx.dataStorage()` 返回可空的 `cn.howxu.mmcr.api.data.view.DataStorage` 视图，底层状态为 `api.data.DataStorage`。它不是 BlockEntity 本身，也不是 `publicapi` 的数据仓库接口。

如果玩家没在 `D` 位置放数据存储方块（或者玩家没成型），这里就是 `null`，整个 tick 直接 `return`。

`storage.get("energy")` 返回 `Optional<api.data.view.DataValue>`，`.asBigInteger()` 只在值实际为 `BigInteger` 时返回非空，不会把其他数值自动转成大整数。视图的 `set(String, Object, Transaction)` 可直接接受 `BigInteger`，但不能接收 `api.dataValue(next)` 生成的底层 `api.data.DataValue`。

### 2. 二分查找最大可入库 FE

```javascript
// every 5 ticks do one input check
if (ctx.isDue(5)) {
    // 本例将单轮请求限制为 INT_MAX，底层能量需求仍使用 long
    var available = ctx.ioView().energyInput()
    var maxRequest = Math.min(available, INT_MAX)

    var low = 0
    var high = maxRequest

    // a binary search for every input hatch for transferLimit
    while (low < high) {
        var candidate = low + Math.ceil((high - low) / 2)

        var probe = ctx.ioPlan()
        probe.addInput(api.energyRequirement(RecipeIO.INPUT, candidate))

        if (probe.simulate().energySatisfied()) {
            low = candidate
        } else {
            high = candidate - 1
        }
    }

    // ...
}
```

`ctx.isDue(5)` 是 MMCR 的"每 N tick 触发一次"工具，避免每 tick 重复跑重活。这里每 5 tick 才尝试一次能量输入。

逻辑：先用 `ctx.ioView().energyInput()` 获取输入端口中的总储量，再用二分查找在 `[0, maxRequest]` 上找当前规划能提取的最大 `candidate`。总储量不等于单次可搬运量，模拟还会考虑端口的搬运限制。每次循环：

- 新建一个 plan（`ctx.ioPlan()`），加入 `candidate` FE 的输入需求 [`api.energyRequirement(RecipeIO.INPUT, candidate)`](../API/KubeJS#energyrequirementrecipemodifieriotype-io-long-fepertick--machinerequirement)
- `probe.simulate().energySatisfied()` 探测这个输入能不能被端口满足
- 能就抬高下限，不能就压上限

最后 `low` 是这轮探测中最大可满足的输入量；二分依赖当前端口对请求量的可满足性单调，不能为任意自定义能力保证这一性质。

`INT_MAX` 限制了这份示例的单轮请求，也使后面的 `intValue()` 转换安全；底层 `EnergyRequirement` 的 FE 数量参数仍是 `long`。

### 3. 入库并持久化

```javascript
if (low > 0) {
    var inputPlan = ctx.ioPlan()
    inputPlan.addInput(api.energyRequirement(RecipeIO.INPUT, low))

    var next = stored.add(BigInteger.valueOf(low))
    var inputSimulation = inputPlan.simulate()

    if (inputSimulation.energySatisfied() && inputPlan.commitData(transaction => {
        // update the data storage value
        storage.set("energy", next, transaction)
    }).successful()) {
        stored = next
    }
}
```

plan 是一次性的，任何提交尝试都会消费它。此处新建 plan，把二分得到的 `low` 拿来重新模拟并正式提交。

注意 `commitData(transaction => { ... })` 的回调：

- `commit(Consumer<TransactionContext>)` 使用 `net.neoforged.neoforge.transfer.transaction.TransactionContext`；`commitData(Consumer<api.data.view.DataStorage.Transaction>)` 把同一事务包装为当前存储视图接受的类型。
- `storage.set(String, Object, DataStorage.Transaction)` 返回 `boolean`，表示值是否改变，不表示事务是否已提交。实际 journal 是内部 `api.data.DataStorage extends SnapshotJournal<Map<String, DataValue>>`。
- IO 全部成功后才调用数据写入回调，再提交根事务。IO 失败不会执行回调；回调抛异常时，参与该事务的 IO / 数据 journal 状态回滚，异常继续向外传播，不是返回一个失败结果。

成功后 `stored = next`，把本地缓存的 `BigInteger` 同步上去。

### 4. 退库

```javascript
// every 5 tick do one output
if (ctx.isDue(5)) {
    // get output capability
    var outputCapacity = ctx.ioView().energyOutputCapacity()

    if (outputCapacity > 0 && stored.signum() > 0) {
        // limit 2.1G
        var requestedBig = stored.min(
            BigInteger.valueOf(Math.min(outputCapacity, INT_MAX))
        )
        var requested = requestedBig.intValue()

        if (requested > 0) {
            var outputPlan = ctx.ioPlan()

            // some output hatches have transformer limit, so OutputPolicy.ALLOW_PARTIAL
            outputPlan.addOutput(
                api.energyRequirement(RecipeIO.OUTPUT, requested),
                OutputPolicy.ALLOW_PARTIAL
            )

            var simulation = outputPlan.simulate()
            var outputs = simulation.outputs()

            if (!outputs.isEmpty()) {
                var accepted = outputs.get(0).accepted()

                if (accepted > 0) {
                    var next = stored.subtract(
                        BigInteger.valueOf(accepted)
                    )

                    // 与 IO 共用事务写入储量；不是 JS Promise
                    if (outputPlan.commitData(transaction => {
                        storage.set("energy", next, transaction)
                    }).successful()) {
                        stored = next
                    }
                }
            }
        }
    }
}
```

关键点：

- `ctx.ioView().energyOutputCapacity()` 拿到所有能量输出端口的总余量。
- 写入方向是 [`RecipeIO.OUTPUT`](../API/KubeJS#recipeio--recipeiovalues)，使用 [`OutputPolicy.ALLOW_PARTIAL`](../API/KubeJS#outputpolicy--outputpolicyvalues) 允许规划少于请求量的输出；`REQUIRE_FULL` 则要求规划能放下全部请求。
- `simulation.outputs()` 的 `.accepted()` 是规划中预计写入输出端口的数量，可能小于 `requested`，不是世界已经接收的数量。
- 内置能量操作提交时必须搬运规划量，实际搬运不足会失败并回滚其 journal 状态。因此只在 `commitData(...).successful()` 后按规划接受量扣账；失败时本地 `stored` 不变。这不是重新模拟后静默接受一个更小的输出量。
- 输入和输出是两个独立事务；输出失败不会撤销同 tick 已成功的入库。

### 5. 控制器屏幕文本

```javascript
if (stored.signum() === 0){
    ctx.screenText().append(
        api.screenScope().OPERATION,
        api.id("mmcr_kubejs:fe_storage_status"),
        Text.literal("No FE stored.")
    )
    return
}
ctx.screenText().append(
    api.screenScope().OPERATION,
    api.id("mmcr_kubejs:fe_storage_status"),
    Text.literal("FE stored: " + api.readableNumberBigInt(stored))
)
```

`ctx.screenText()` 获取底层 `api.controller.ControllerScreenText`，不是启动注册用的 `ControllerScreenTextEventJS`；这里的 scope / ID 分别由 `api.screenScope().OPERATION` / `api.id(...)` 提供。

[`api.screenScope().OPERATION`](../API/KubeJS#screenscope--screenscopevalues) 会参与运行时的操作文本清理；本例每 tick 写入同一 scope / ID，`append` 替换该键已有内容。没有配方不等于该 scope 永远不会被清理，文本显示还取决于控制器刷新与同步。

[`api.readableNumberBigInt(stored)`](../API/KubeJS#readablenumberbigintbiginteger-value--string) 把 `BigInteger` 渲染成紧凑字符串，适合屏幕槽位显示。底层对应 [`api.presentation.ReadableNumber`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/api/presentation/ReadableNumber.java)。

[`api.id("mmcr_kubejs:fe_storage_status")`](../API/KubeJS#idstring-id--identifier) 把字符串解析成命名空间 ID，作为屏幕文本行的 `lineId`。同一 `lineId` 反复 `append` 会替换内容，实现"幂等覆盖"。

> JADE 文本：本机器没有调用 `ctx.jadeText()`。Jade 文本与屏幕文本是两条独立通道。

## 特殊机制

### 事务感知的 `DataStorage`

运行时拿到的是存储视图；它代理的底层 [`api.data.DataStorage`](https://github.com/Nibelungorum/ModularMachinery-Community-Refoxed/blob/f234477b/src/main/java/cn/howxu/mmcr/api/data/DataStorage.java) 继承 NeoForge 的 `SnapshotJournal<Map<String, DataValue>>`。视图的当前签名如下：

| 方法 | 返回值 / 含义 |
| --- | --- |
| `get(String key)` | `Optional<api.data.view.DataValue>` |
| `contains(String key)` | `boolean` |
| `values()` | 不可修改的 `Map<String, api.data.view.DataValue>` 快照，不是实时可变 Map |
| `set(String key, DataValue value)` / `set(String key, Object value)` | `void`，立即写入 |
| `set(String key, DataValue value, Transaction tx)` / `set(String key, Object value, Transaction tx)` | `boolean`，加入事务 journal，表示是否改变 |
| `remove(String key)` | `Optional<api.data.view.DataValue>`，立即删除；当前没有事务删除重载 |

其中 `DataValue` / `Transaction` 指 `api.data.view` 的类型，`Transaction` 是 `DataStorage` 的嵌套类。键不能为 null 或空白。

使用底层 `MachineIoPlan.commitData(...)` 获得对应视图事务：

```javascript
plan.commitData(transaction => {
    storage.set("energy", next, transaction)
}).successful()
```

提交前必须先 `plan.simulate()`；`commitData` 不会自动模拟。参与该事务的存储写入在根事务未提交时可回滚。普通 `set`、`remove`、屏幕更新、网络发送、闪电或爆炸不会自动加入 journal，即便写在提交回调里也不能承诺原子回滚。

存储视图的 `Object` 重载会通过 `api.data.view.DataValue.from(...)` 包装支持的值；本例直接传 `BigInteger`。底层 `api.data.DataValue`、视图 `api.data.view.DataValue` 和 Java `publicapi` 的数据值不是可互换的同一个类。

### `BigInteger` 计数

`BigInteger` 比 `long` 慢，但能容纳任意大小的累加值。如果你的存储机器能量单位是 FE，每 tick 几百 FE，用 `long` 即可。如果你想模拟一个"无限水库"，例如宇宙能量、模组自定义能源，`BigInteger` 永远不会溢出。

源码里 `Math.min(outputCapacity, INT_MAX)` 是把 `long` 输出容量截到 `int`，方便 `BigInteger.intValue()` 安全转换。

### 探测-提交分离

二分查找只调用 `simulate()`，永远不 commit，真正写入走第二个独立的 plan。这是 `MachineIoPlan` 一次性原则下的写法。一次 plan `commit` 后就失效了，**第二次**新建 plan 才是正式的 commit。

### 两种 `DataValue` 的边界

[`api.dataValue(value)`](../API/KubeJS#datavalueobject-value--datavalue) 生成底层 `api.data.DataValue`，适用于网络处理器收到的底层存储等入口。`ctx.dataStorage()` 则返回存储视图，应直接传支持的原始值，或使用 `api.data.view.DataValue`。本例往返为：

- `storage.set("energy", next, transaction)`：由视图包装 `BigInteger` 并加入同一个 IO 事务

- 接受侧 `saved.get().asBigInteger().orElse(BigInteger.ZERO)`，从 `DataValue` 安全取回 `BigInteger`

KubeJS 端支持的取值方法不止 `asBigInteger`，还有 `asBoolean` / `asString` / `asInt` / `asLong` / `asFloat` / `asDouble` 等。
